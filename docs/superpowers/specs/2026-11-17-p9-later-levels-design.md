# P9 后面关卡完善 — 设计/结论文档

- **日期**: 2026-11-17
- **分支/标签**: `feat/p9-later-levels`（提交落在 main 上，tag `v0.16-p9-later-levels`）
- **上游**: P8 正确性体检（`v0.15-p8-integrity`，见 `docs/superpowers/plans/2026-11-17-p8-integrity.md`）
- **用户诉求**: "整体不错，继续完善后面关卡"

## 1. 目标与判据

"完善后面关卡"如果理解成"把 README 限制清单挨个补齐"，会掉进两个坑：
一是把**无法验证的规范**当已知事实来实现（special 编号表全靠记忆），
二是把**模型的缺陷**当成引擎的缺陷去修（可达性模型说"这关打不通"，其实是模型看不懂）。

所以本轮的判据定成三条：

1. 引擎必须能说出"我支持哪些 special"——**只有一个来源**，不能是三份会漂移的清单。
2. 任何 special 的语义，必须由手上的关卡数据**确认或否证**之后才实现。
3. 关卡"能不能打通"这类问题，如果只能用模型回答，就**不许变成 gate**。

## 2. 做了什么

### 2.1 special 分派表（前置条件）

P6a 的 spec 本来就要求"special 分派表：纯数据"，但代码长成了一份 switch +
两份重复的编号清单（`triggerFor`、`keyForSpecial`）。本轮合并成一张
`SpecialDef {special, kind, trigger, key, speed}` 表，`P_ActivateLine` 按 kind 分派，
`triggerFor` 与钥匙要求都从同一行读。

判据：**不改任何测试、220/220 全绿**——这就是"这是搬家不是重写"的证据。
这一步的真正价值不是整洁，而是让诊断工具能问引擎"这条线你操作得了吗"
（`P_LineSpecialSupported` / `P_IsExitSpecial`），而不是问一份可能过期的抄本。

### 2.2 两个新 special：61 与 112

体检给出的工作清单收敛到两个数字。对它们的处理走了本轮最重要的方法：

- 第一次探针报告"它们的 tag 在地图里不存在" → **这个结论是探针自己的 bug**
  （脚本中途崩溃，恰好崩在该打印的行上）。重做后确认 tag 存在且指向可动扇区。
- E4M7 line 1061：从 sec 222(fl 64/cl 128) 跨到 sec 219(fl 88/cl 128)，
  opening = 128−88 = 40 < 56，**只有把远处扇区的地板降下来才走得通**。
  E4M4/E1M5 的 112 线是同一个形状。
- 于是两者都实现为 `FloorLower`（速度 4），方向就是地图几何自己要求的方向。

诚实地说清楚边界：**可达性工具无法区分方向**（它的规则是"有任何受支持的 mover
作用在这个扇区 ⇒ 这条边算通"），所以方向不是被它验证的，是被**单元测试钉住**的：
合成地图里开关触发后，被 tag 的地板必须降到房间那一层。

### 2.3 被否证而没有实现的东西

| 编号 | 出现次数 | 为什么不做 |
|---|---|---|
| 48 | 336 线 | 落点物件既不在线背面也不在 tag 扇区里 → **不是传送**；272 条还是单面线 |
| 123 | 78 线 | 同上否证；且相邻扇区常是 floor>ceiling 的实心岩石 |
| 18 / 12 | 12 / 4 线 | 语义无法从手上的数据判定；且被卡住的地图里**根本没有这两个编号**，实现它们不会解锁任何一关，只会引入一个可能把玩家提前送出关卡的 bug |

P8 时"48/123 不是传送"的否证是同一套方法的第一次成功；本轮把它写成了规则：
**记忆不可验证时，让地图作证；地图不作证时，写进已知限制，不猜。**

## 3. 本轮最大的收获其实是两个**失败**的工具

### 3.1 `--reachtest`：静态扇区可达性

扇区图 BFS，边可过的条件：几何能走 / 受支持的 mover 能打开 / 受支持的传送能跳。
为了让它有意义，改了三次模型：

1. 姿态与 tag 之外，必须承认 **tag=0 的开关线**（"门就在这条线的另一侧"）；
2. 必须承认**地板是可以动的**（把扇区地板建模成一个区间 `[floor, ceiling-56]`，
   否则"坐电梯过去"的边全部被当成墙）；
3. 必须区分**实心岩石**与**关闭的门**——两者都是 floor≥ceiling。
   第一版把"进退化扇区的边"一律跳过，于是**门也全被跳过**：E4M7 的可达扇区
   从 648 掉到 4。修正为"只在没有任何东西能移动它时才算岩石"，并且
   **不对玩家所在那一侧做同样检查**（已经站上的门洞必须还能穿到对面）。

即便如此，它仍报告 15 张图"打不通"，而这些图的边界边**一个都不带未实现 special**。
结论：这是模型的盲区（看不懂"电梯只升到一半才够踩上台阶"、看不懂"钥匙被怪守着"、
看不懂"三间房之外的开关"），不是引擎的缺陷。

**所以它不是 gate。** 代码注释里写明了这一点，以及它唯一合法的用法：
把 gating 列表读成"值得实现的 special 清单"，别的一律不读。
`--frontier <map>` 就是为了区分两者而加的：它打印"贴着可达区域却过不去"的每条边，
连同 opening/step/special/tag 的数字。

### 3.2 `--solvetest`：目标导向漫游

从每个种子点朝最近的出口线走、走不动就 use、让引擎自己的门/电梯/传送去解决问题。
36 张图解出 7 张。这个结果**主要反映的是贪心漫游器不行**，不是关卡打不通。

它唯一的单向价值：**它解开的图，是真实引擎代码可通的证明**
（每一步都经过 `P_TryMove` / `P_UseLines` / `P_RunThinkers`）。
它解不开，什么都不能说明。同样不做 gate，注释里写清。

## 5. 遗留（后面关卡真正还缺的东西）

1. **静默 crusher / 真正的楼梯生成器**：vanilla 的楼梯是"反复认领相邻扇区逐级建造"，
   本引擎是"每个 tag 扇区抬 8"。目前没有任何体检证据说明它卡住了某张图，
   所以没有以猜的方式改它。
2. **door 联动灯光类型 1/2/4/15/16**：灯光类型表里这几个与门的等待时间耦合，
   需要先把门模型扩展成"能同时驱动扇区灯光"的形状。
3. **18/12 出口变体**：见 2.3，等语义可验证时再做。
4. **怪物寻路**：简化的 ±45/±90 绕行会在走廊里排队；完整的
   `P_NewChaseDir` + 避让同类是一笔独立投入。
5. **teleport fog、菜单/难度选择、TAB 自动地图、OPL 音色**：观感与功能项，未动。

## 6. 流程上记下来的一条

本轮出现两次"工具自己错了，结论看起来像引擎错了"：探针脚本崩溃导致的
"tag 不存在"，以及可达性模型把关闭的门当岩石而砍断了门遍历。
两者的共同点是：**诊断工具的输出在被当作事实之前，需要先被反证一次**——
要么用另一条独立路径复现（换探针实现、直接读原始字节），
要么看它是否违反某个已知为真的边界条件（E1M1 明明能打通，模型却说打不通）。

这条已经写进 `docs/guide/16-验证方法论.md` 的"诚实规则"一节。

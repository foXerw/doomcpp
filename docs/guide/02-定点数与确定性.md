# 02 定点数与确定性

## 不做这件事会怎样

有三个 bug，几乎所有自写引擎都会遇到，而它们的根因都是"数值表示选错了地方"。

**其一，越玩越歪。** 玩家贴着墙滑行，每 tic 做一次 `位置 += 速度向量`。浮点的小数残差每 tic 攒一点点，四千年后（实际上大约几千 tic）他的 x 坐标和墙壁的距离不再等于当初算出的那个值——某一 tic 的"能不能过去"判定翻转了，人掉进墙里。定点不会消失误差，但它的误差是**可复现**的：同一条路线、同一串 ticcmd，每次都卡在同一格，所以你至少能观察它、修掉它。

**其二，存档读回来人挪了。** 存档的本质是"把世界的整数状态写下去，再原样读回来"。一旦状态里混进浮点，你要么冒着跨编译器不一致的风险存二进制浮点，要么写 `%.3f` 丢精度然后接受"站在压力板上的玩家读档后不在压力板上了"。

**其三，回放对不上。** 录下 ticcmd 想复现一局游戏，前提是"同样的输入 → 同样的模拟"。`sin()`、`atan2()` 这类 libm 函数**不保证**跨平台、跨版本给出同一个值；编译器还允许把 `a*b+c` 收缩成一条 FMA，改变最后一位。少一个判据的分支走错一次，第 200 关的怪物就会出现在不该出现的地方。

这三条的共同解药是同一件事：**让模拟的每个数值都是整数，让每个函数都是你自己写的。**

## 16.16 定点

```
fixed32 = int32，低 16 位是小数
    值 = 原始整数 / 65536
    FRACUNIT = 1 << 16 = 65536        // 这就是"1.0"
    地图单位 u  →  u << 16
    范围 ±32767.99998，分辨率 1/65536 ≈ 0.0000153
```

1993 年需要它，是因为目标机器（486SX、笔记本版 386）常常**没有浮点单元**，软件浮点仿真比整数慢一到两个数量级；而 DOOM 的热点恰恰是每帧几万次的乘法——每列墙一次斜率乘法、每个精灵像素一次纹理坐标乘法、每 tic 每个物件一次移动分解。定点把这些都变成"整数乘 + 移位"。

```
FixedMul(a, b):                       // a*b，仍为 16.16
    return (int64)a * (int64)b >> 16

FixedDiv(a, b):                       // a/b，带饱和保护
    if (abs(a) >> 14) >= abs(b):      // 商必然超出 32 位
        return ((a ^ b) < 0) ? MININT : MAXINT
    return (int64)a << 16 / b
```

**天真写法在哪里溢出。** 两个 16.16 相乘是 32+32=64 位结果，如果你写 `a * b >> 16` 而 `a`、`b` 都是 int32，乘法在 32 位里就完成并**静默丢弃高位**：`2.0 * 2.0`（131072 × 131072 = 2³⁴）回绕成 0，你会得到"两点距离是零"这种荒谬结论。同理 `(a << 16) / b` 的移位也会把有效位推出符号位，必须先加宽再移。FixedDiv 的饱和保护不是装饰：`距离 = FixedDiv(垂直差, 斜率)` 里斜率接近 0 的情况在真实关卡里天天出现（水平面的投影），钳到最大整数正好等价于"这条射线打到无穷远"，而让它溢出回绕会给你一个负数深度——渲染器会把背后的墙画到前面来。

还有一个纯语法层面的坑：**右移不是除法。** 对负数，`x >> 16` 向 −∞ 取整，`x / 65536` 向 0 取整，两者差一个 ulp。一旦代码里两种写法混用，边界判定会抖：贴边的那一列今天算"在里面"，明天算"在外面"。全书约定——所有定点缩放统一用移位，所有需要"取整到地图单位"的地方显式写清是向下取整还是四舍五入，并且只用一种。

## 开方，以及为什么几乎不需要它

```
FixedSqrt(a):                         // a 为 16.16，结果仍为 16.16
    if a <= 0: return 0
    n = (int64)a << 16                // 相当于 a × 65536
    整数牛顿迭代: y = (x + n/x) / 2，直到收敛    // 全整数，无浮点
    return y
```

它存在的理由是"有时候确实要一个真实长度"（比如按距离决定精灵缩放）。但在判定类代码里，你几乎从不需要它，因为有两种便宜得多的替代：

**比较平方而不是开方。** `dx*dx + dy*dy < r*r` 用两次 `FixedMul` 和一次整数比较就够了，没有除法、没有迭代、没有精度问题。凡是"够不够得着""在不在射程内"，先问一句能不能改成平方比较。

**用八边形近似代替圆。** DOOM 到处用的是这个：

```
P_AproxDistance(dx, dy):
    dx = abs(dx); dy = abs(dy)
    return (dx + dy) - min(dx, dy) / 2      // 除法即右移，1 次移位 2 次加减
```

设真距离为 1，看它给出什么（它总是**高估**）：

| 方向 | 真距离 | 近似值 | 误差 |
|---|---|---|---|
| 正东 / 正北（轴向） | 1.000 | 1.000 | 0% |
| 45°（对角） | 1.000 | 1.061 | +6.1% |
| 约 26.6°（最坏处） | 1.000 | 1.118 | +11.8%（= √5/2，这是上界） |

看到 12% 别慌，理由有两层。**第一，几乎所有用法都只是比较，而阈值是拿同一个近似量标定出来的。**"怪物能不能看见玩家""多远开始追击""攻击够不够得着"这些数字当初就是按近似距离调的，换成精确开方反而要让每一个阈值重调一遍——那种"改了更正确的数值，手感全坏掉"的返工，比误差本身贵得多。**第二，误差的方向是固定的：近似值永远不小于真值。** 所以 `P_AproxDistance < 射程` 蕴含"真的在射程内"，判定的有效区域是一个内接于目标圆的八边形：它可能拒绝一个刚好在边缘的目标，但绝不会接受一个真的够不着的目标。对游戏来说，"偶尔保守"是可以接受的，"偶尔越界"是要命穿墙的那一类。

## BAM 角：整圈 2³²

```
angle_t = uint32
    整圈 = 2³²
    ANG45  = 0x2000_0000     ANG90  = 0x4000_0000
    ANG180 = 0x8000_0000     ANG270 = 0xC000_0000
    1 度   ≈ 0x00B6_D381
    约定：angle=0 朝东（+X），逆时针增大（+Y 为北）
```

好处一：**没有归一化这件事。** 加减角自动回绕，`viewangle ± ANG45` 直接给出 90° 视场的两条边——即使 `viewangle` 靠近 0、下边界"减成负数"也无所谓，无符号回绕后的那个值仍然是正确的角度，不需要 `% 360`，也不需要 `if (a < 0) a += 360`。

好处二：**"哪一侧"变成一次无符号比较。**

```
// 目标在视线的哪一边？
rel = targetang - viewang            // uint32 减法，越界自动回绕
if (rel < ANG180)  → 顺时针那一侧
else               → 逆时针那一侧
```

如果用有符号角度，你得先把它塞回 [−180°, +180°)，那需要两次带分支的比较；无符号回绕让减法顺手就把结果放到了"从 0 开始沿顺时针方向量"的坐标里，一次比较搞定。精灵的八方向选帧、怪物视野锥判定、BSP 遍历的转向判断，全都靠这一招。代价是边界归属：`rel == ANG180`（正好在背后）永远落到某一个分支里，你必须**明确知道它落在哪个**，因为"视线刚好擦过一面墙"时，这个决定就是"这一列画不画"。

好处三：查表把三角函数彻底消掉。

```
FINEANGLES = 8192                        // 整圆 8192 份，每份 ≈ 0.0439°
ANGLETOFINESHIFT = 19                    // 2³² >> 19 == 8192
fine = angle >> 19                       // BAM → 表下标
dx   = FixedMul(dist, finecosine[fine])
dy   = FixedMul(dist, finesine[fine])
```

表只存四分之一周期，`finecosine = finesine + FINEANGLES/4`（数组实际长度是 `5*FINEANGLES/4`，多出来的那一个四分之一周期是为了让余弦在整个圆周上索引都不越界）。启动时真正**算**出来的只有 512 个点（`FINEANGLES/16`），每 16 个一组，组内剩下的 15 个用线性外插补齐——因为在定点精度下，1/8192 弧度的正弦本来就只有几位有效数字，插值不会产生看得见的误差。幅度是 `FRACUNIT`，即 sin/cos 的定点 1.0。

于是整个引擎的热循环里**没有任何一次 libm 调用**：移动是两次查表 + 两次定点乘，转向是整数加减，`R_PointToAngle` 反过来用一组按象限准备的定点斜率做除法。这不是怀旧，这是确定性的来源：查表的结果永远相同，libm 的结果不一定。

## 确定性换来了什么

一旦"同样的输入必然产生同样的状态"成立，两件本来需要奇迹的事情变成常规：

```
存档 = 遍历 thinker 链表，把每个物件的整数状态 + 随机数表下标 + 关卡计时器写盘
回放 = 只记每 tic 的 ticcmd（十几字节），读的时候把 cmd 重新喂进同一条逻辑
```

注意存档不需要包含"画面"，也不需要包含任何派生量：可视平面、vissprite、裁剪数组都是每帧现算的，存下来反而是错的。同样，回放不需要录屏——它录的是**意图**，模拟自己会重演一切。这也是为什么第 16 章的很多检查能写成"跑 N 个 tic 然后断言"，而不需要任何图像比对。

顺带列出会悄悄破坏确定性的东西，它们都不是显而易见的 bug：编译器把乘加收缩成 FMA；`long double`/x87 的 80 位中间量；哈希容器（如 `unordered_map`）的遍历顺序；未初始化的对齐填充位被写进存档；用系统时钟而不是关卡 tic 驱动动画。

## 诚实的取舍：哪里定点，哪里浮点

| 子系统 | 建议 | 理由 |
|---|---|---|
| 碰撞与移动 | **定点** | 位置必须可复现；"能不能通过这条缝"必须永远给同一个答案；漂移会累积成穿墙 |
| 关卡机关 / 思考者 | **定点** | 高度、计时器、持续时间要进存档，且门不能因为浮点差停在 0.9999 |
| 命中判定、随机数 | **定点 + 表** | 想要回放或想验证"打了 1000 次伤害的分布"时，唯一的前提是可复现 |
| BSP 遍历的边界判定 | 定点 | 它是纯整数叉积，浮点反而引入"共线时算哪边"的随机性 |
| 渲染的每像素算术 | **可以用浮点** | 判据是"看起来对"，不是"逐位对"；它不写世界状态，因此不影响模拟 |
| 音频混音 | 可以用浮点 | 除非你要回放的音频也逐位一致 |

关键的认识是：**确定性只在"状态会被保存或被重演"的地方是硬要求。** 渲染是状态的消费者，不是生产者；只要它不反过来写世界，用浮点不会污染存档。

## 一个具体的陷阱：把能跑的浮点渲染器事后改成定点

这件事值得单独一节，因为它看起来像"提高精度"，实际是在改**约定**。

示例仓库里真发生过一次：渲染核心已经用浮点跑通，测试与画面都正常。有人把逐列投影换成定点，理由是"更忠实"。改完之后，同一段固定路线上，"坑洞里没被任何平面盖住的像素"（一个常驻的自动检查项）从 65 个涨到大约 25000 个。因果链是这样的：

```
定点化 → 斜率与截距的取整方式变了
       → 同一面墙的边落在哪一行屏幕像素变了（差 1 行）
       → 相邻两个 seg 对同一列的裁剪区间 [lo, hi] 不再互补
       → 某段区间既不属于前一个 seg 也不属于后一个 seg（缝），或者两者都画（叠）
       → 可见的空洞成片出现
```

这里没有"定点的 bug"，也没有"浮点的 bug"。这是一个**设计耦合**：数值表示和边界收口约定（`<=` 还是 `<`、要不要 `+1`、开口区间怎么取整）是一体的。你把取整模式换掉，就等于把所有"这条线结束在哪里"的隐含答案同时挪动了半格。任何改动取整的重构，都必须同时重新审视每一处收边，否则你会得到一份"每个局部都更精确、整体却漏风"的渲染器。

由此得出一条实用规则：**先让一个子系统用一种表示彻底跑通并被自动检查覆盖，再考虑换表示。** 有基线时，回归是 65→25000 这种一眼可见的数字；没有基线时，它只是一张"看起来还行"的截图。那次尝试最终被整体回滚。

## 这样做的代价 / 放弃了什么

- **范围与分辨率是硬约束。** ±32767 地图单位、1/65536 的最小步长。极小的量会直接归零（一个 `FixedMul(很小的数, 很小的数)` 得到 0），所以累加类计算要记得先放大再缩小。
- **溢出是静默的。** 浮点溢出给你 `inf`，定点溢出给你另一个数。`FixedDiv` 的饱和保护是人为加的补丁，不是语言帮你做的。
- **不能随手 print 小数。** 调试器里看到 `196608`，你得自己心算那是 3.0。这是纯摩擦，没有好处，只能靠一个 `FIX2NAME` 类的打印辅助缓解。
- **性能理由在今天已经不成立。** 现代 CPU 上一次标量浮点乘法和整数乘法一样快，SIMD 浮点更快。所以本书在渲染这一侧不坚持定点：为它付的确定性成本换不到回报。定点剩下的真实价值只有一个——**可复现**，而可复现只在会被保存和重演的那个世界里才值钱。
- **放弃了硬件加速的数学风格。** 齐次坐标、透视除法、深度缓冲这一整套现代写法，与"逐列扫描 + 整数裁剪"的世界观互不兼容。你可以混着写，但每混一处，就要在第 16 章里多补一条不变式检查。

# 11 · 关卡机关 specials

> 这一章的主体不是编号清单，而是一种方法：在拒绝抄原版源码的前提下，如何从手上的地图数据**反证**一个 special 编号的语义——以及当数据拒绝回答时，该怎么办。

## 不做这件事会怎样

- **开错门。** 按"门在按钮同一侧"的直觉实现，一半关卡的门纹丝不动、另一半开了隔壁。原因是编号语义里藏着一条没人告诉你的规则。
- **三份互相矛盾的答案。** 动作代码里一个 switch、"支持列表"里一组 if、钥匙需求里一张小表——同一个编号被回答了三次，改一处漏两处，可达性工具开始撒谎。
- **地板走进天花板。** 一个开关同时动了地板和天花板，起始时钳制过一次就再没管，几 tic 后地板穿过正在下降的天花板，玩家两脚悬在天花板贴图里。
- **猜出来的机关。** 按社区表格猜某个编号"大概是传送"，实现了，测试全绿，截图正常——直到玩家走到某个角落，一条语义错误的 walk 触发线把他扔进不该去的地方。猜错的机关没有报错，只有静默的关卡破坏。

## 两个通道：触发器与命名

原版的机关系统只有两个通道：

- **线 special** = 玩家触碰到的**触发器**。它自己几乎不携带"动谁"的信息。
- **扇区 tag** = 被移动对象的**名字**。门、电梯、地板属于某个带 tag 的扇区。

开关和门通常**是两个不同物体**，中间只有 tag 相连。为什么这么设计？因为关卡编译器根本不可能知道"这个按钮影响哪些扇区"——那是作者的意图，不是几何属性。所以引擎永远不要试图从位置推断意图（门的例外见下文），一切远程效果走 tag。

## 一张表是唯一的事实源

每个支持的线 special 用一行描述：

```text
SpecialDef { number, kind,          # 动作种类：门/电梯/地板/传送/出口…
             trigger,               # 位掩码：1=use(空格键)，2=walk(跨过)
             key,                   # 需要的钥匙位或 0
             speed, wait }          # 运动速度、开到位后的等待 tic
```

分派器读它，工具（可达性审计："玩家能不能操作这条线？"）读**同一张表**。这是全部要点：supported 的清单和代码的行为之间不存在第二个副本，因此不可能漂移。

漂移版本的长相：动作 switch 一处、`isSupported()` 列表一处、钥匙表一处。三份答案对一个问题，于是新增一个 special 要同步三处——漏掉的那处必然存在，而且通常错在**工具侧**：审计说这关不可达，其实引擎能开门；或者反过来，审计把不支持的线当成可操作，把"可解"的错误结论喂给验证。

## 触发类别：位掩码不是枚举

use 与 walk、一次性与可重复，是两个正交维度。可重复性藏在纹理名里（SW1→SW2，见后），触发方式则必须用**位掩码**，因为实践中出现过一个编号需要**同时**两种触发：同一个 IWAD 里，传送效果有的被作者做成墙上的按钮（use），有的做成脚下的垫子（walk）——同一个编号，两种排版。用 enum 的实现会在其中一半关卡里失灵。顺带一条同族的教训：一次性 vs 可重复也对应成对编号（1 与 90 是"可重复版"），漏了这个成对关系，关卡里所有"门永远关不上"。

## 门：门扇区在玩家的对侧

手动门是 tag 通道唯一的例外：**门所在的扇区是"激活玩家的对侧"**（作者可能把门按钮放在线的任一面，但对侧的扇区才是门洞本体）。实现就是对激活者位置和线的方向做一次叉积定侧。按"固定取 front sidedef 的扇区"来实现，效果是：**取决于作者画线的方向，一半关卡的门开错对象**——这是复刻时最常见的单个实现级 bug。

开到位的高度 = 邻接扇区中最低的天花板 − 4（这道缝让门顶不邻接天花板等高相撞，也保住了视线/开口判定的下沿行为），下限是门扇区自己的地板 + 1。开 → 等待 150 tic → 关。**正在关闭的门每 tic 检查：新高度若会压到扇区内任何站立物件的头，立即反转重开**（等待清零）。这一条不做，门会变成无差别绞肉机，玩家被卡在门里活活压死——原版的门是礼貌的。

## 升降台、地板、天花板：目标全从邻接几何算

| 动作 | 目标高度公式 |
|---|---|
| plat/电梯 | 升到 nearest-up：邻接扇区中**最近的更高**地板 |
| 地板下降 | nearest-down：邻接中**最近的更低**地板 |
| 地板上升 | nearest-up（同上） |
| 天花板升到邻接 | 邻接扇区最低天花板 − 4 |
| 天花板降到地板 | 门/压扁场景：本扇区地板高度 |

找不到邻接时的兜底值（±64）是本地标定——原版行为无法从数据判定时，本书规则：选自洽值并注明，不声称与原版逐值一致。

**钳制规则：任何表面永远不许越过对面表面**（地板 ≤ 天花板）。关键细节是这条必须**每 tic 重算，不是启动时算一次**：地板朝"邻接高度"上升时若目标高于自家天花板，要当场截短；而同一条开关线可以让地板和天花板**同时**运动——只在启动时钳制，地板就会穿过正在下降的天花板，玩家两脚站进天花板内部（doomcpp 的 clipaudit 在 E1M7/E3M5 抓到的正是它，因为起始钳制用的是对方的旧高度）。

运动中的扇区每 tic 要把内部物件"带"到位：重算它们的 floorz/ceilingz/z。而带不动的那个分支就是下一章的主角——

## 压顶机关：不是特例，是钳制 + 伤害规则的推论

空间容不下人时会发生两件事：天花板**不许**把物件压到地板以下（第 10 章的退化规则），于是"没有空间"必须用另一种方式表达——对任何还活着的可伤害物件判压碎（大数额伤害）。压顶机关（crusher）在此之后只需要"会回来"的天花板循环，不需要任何专属伤害代码。反过来说：如果实现里只有钳制没有伤害，玩家会安静地嵌进天花板看贴图内部——几何上"没越界"，观感上引擎在和地图吵架。

## 如何知道 special N 是什么意思：用地图反证

不抄源码，语义从哪来？**问 shipped maps 投票。**方法：

1. 从社区文档列**假设**（"39 是传送，落点由 tag 决定" / "落点在线的另一侧"）。
2. 对 IWAD 全部 35 关里出现的该编号线，统计其上下文：front/back 扇区是谁、tag 有没有扇区认领、地图上所有**传送落点 thing（类型 14）**经真实 BSP 解析落在哪个扇区。
3. 逐编号验证：**落点扇区 == 线对侧扇区？还是 == 携带线 tag 的扇区？还是都不是？**

teleport 家族的实际结果：

| 编号 | 数据投票 | 结论 |
|---|---|---|
| 39, 97 | 落点 thing 全部在**携带同 tag 的扇区**里 | 按 tag 传送，walk 触发 |
| 125, 126 | 落点 thing 全部在**线的对侧**（或踩垫者自己所在的扇区） | 对侧传送；且 use 与 walk 排版并存 → 触发位掩码 = both |
| 48, 123 | **两者都不是**：附近既无 tag 扇区、对侧也无处可落 | 不是传送 → 拒不实现，记录在案 |

这张表的价值在于它**证伪了两次流传说法**：48/123 在社区编号表里长期被标注为 teleport——数据说不是，社区表错了。"tag 还是对侧"也不是教条：39 与 125 同族同功能，答案不同，只有逐个问地图才知道。

由此立规：**凡不能从数据确认语义的 special，不实现，并写进"未实现清单"文档。**宁可不响应，不可猜着响应。猜错的机关静默破坏关卡——没有崩溃、没有红测试、截图里一切正常，只有玩家走到某个角落时被一条本不该有反应的线扔进不该去的地方。"什么都不做"是唯一可证的行为。方向无法判定的编号（如 61/112 升还是降）可以再加一票：让求解器/可达性审计投票——哪种赋值能让关卡保持可解。

## 开关纹理：改内存副本，不改 WAD

"按钮按下后变红"的实现是一行字符串变异：`SW1xxx → SW2xxx`（第三个字符 1→2）。**按下与否的状态就编码在名字里**，不需要给每面墙加 bool——纹理名前缀本身就是标记位。两个纪律：只改**加载后的内存数据**（WAD 是只读档案，且第 03 章的贴图库按名字索引，改包等于污染所有共享它的东西）；这和第 04 章"派生数据放内存"同源。只换 first side 的匹配面即可，别把整条线两面都换亮。

## 秘密扇区：扇区类型，不是线类型

秘密是**扇区**的 special（9），与任何线无关。判定只有一个：玩家所站扇区类型 == 9 → 计入。记账必须**每扇区一次**：一个 bool 数组（长度 = 扇区数），踩过就置位——否则来回走动会让结算画面的 secrets% 涨到三位数。

## 这样做的代价 / 放弃了什么

- **一张表**的表达力被行结构锁死：将来要加"带伤害类型的压顶""带步数的楼梯"，得扩行字段，而不是加一个 case。这是用结构换防漂移的长期税。
- **地图反证只在编号实际出现时有效。** 某编号若只在某张图出现一次，统计给不出置信；若根本没出现（大量后期 special），它只能停留在未实现清单里等待外部资料——本书接受这个天花板，并把清单当作可信交付物。
- 未实现清单本身是负担：工具必须诚实上报"这条线的 special 不支持"，否则可达性结论被悄悄乐观污染。
- 门的"对侧"规则只适用于手动门；远程门仍然走 tag——两套寻的通道并存，比纯 tag 方案多一个特例。我们付这个特例的钱，因为关卡数据收了这份税。

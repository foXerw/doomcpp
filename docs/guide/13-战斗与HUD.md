# 13 战斗与 HUD

## 不做这件事会怎样

战斗手感不来自伤害数值，来自状态流转的节奏。武器状态机写错，切枪会跳帧或者在抬枪过程中开火；把"按住开火"建模成事件，连发枪就变成玩家要点两百次的单发枪；hitscan（即时命中射线）的垂直判定错一条，就会出现"明明打中墙，隔壁房间的怪物却掉了血"；拾取判定写成"先拿走再决定效果"，玩家会当着面丢掉道具。而 HUD 会每一帧都对玩家撒谎——并且是所有自动化测试里最察觉不到的那类谎，因为测试断言的是字段，玩家看到的是像素。

## 13.1 武器：五状态机 + 一次 pending 握手

武器不是一个函数，而是表里的一行。`weaponinfo` 每种武器占一行：

| 字段 | 含义 |
|---|---|
| ammo | 弹药种类；拳头/电锯取"无需弹药"列 |
| readystate | 待机（屏下垂手的动画帧） |
| atkstate | 开火序列入口 |
| upstate / downstate | 举枪 / 收枪动画入口 |
| flashstate | 枪口火光序列（画在第二个槽位） |

屏上的武器叫玩家精灵（psprite）——它是独立于地图物件（mobj）状态机的小状态机，只有两个槽位：0 = 武器本体，1 = 枪口火光。每逻辑帧（tic）倒计时，到 0 进入 nextstate 并立刻执行该状态自带的 action。整个切换逻辑只有四个 action：

```text
action A_WeaponReady(p):                    # 待机中的每个 tic
    if p.pending != NONE:                   # 有切枪请求
        goto weaponinfo[p.ready].downstate  # 开始收枪
    elif p.attackDown:                      # 开火键还按着
        goto weaponinfo[p.ready].atkstate   # 开始开火序列
action A_Lower(p):                          # 收枪动画结束
    p.ready = p.pending; p.pending = NONE
    goto weaponinfo[p.ready].upstate        # 立刻开始举新枪
action A_Raise(p):                          # 举枪动画结束
    goto weaponinfo[p.ready].readystate
action A_ReFire(p):                         # 开火序列走完
    if p.attackDown and hasAmmo: goto atkstate
    else: goto readystate
```

关键点：按数字键 2 只写 `pendingweapon = 2`，不碰任何画面。提交发生在收枪动画末尾的 A_Lower 里。这个握手同时买到两件事——切枪的响应在一个 tic 之内（手感"即时"），而动画一帧不跳（因为提交点在动画中段，不在按键的瞬间）。不要做"直接切到新枪的 atkstate"这种优化：旧枪正在下移时不允许新枪开火，这条规则不靠防御性检查，是状态机自然长出来的。

## 13.2 开火键按着，是逐 tic 的输入状态，不是事件

宿主层每 tic 传两类输入："Ctrl 当前按着吗"是 bool 状态，"刚才按了数字几"是事件。两者不能互换。开火是状态：A_WeaponReady 和 A_ReFire 每个 tic 重新读它，连发武器因此能按住扫射；若把开火建模成事件，玩家按住不放只会打一发。

值得说清楚的是"单发/连发"在实现里的真相：原版语义下，两类武器其实都在开火序列结束时检查按键仍按住就再来一发——区别只在序列把 A_ReFire 检查点放在动画的哪里、周期多长。机枪四 tic 到检查点，霰弹枪四十 tic。所以"单发武器"的手感来自动画长，而不是"必须松开重按"。真想实现严格的一按一发，就得对 attackDown 做边沿检测——那是一个不同的设计，改之前先知道自己改的是什么。

## 13.3 弹药：每种类型独立计数、独立封顶

四种弹药（子弹/ shells/电池/火箭）各占两个数：当前值与上限。上限来自表；背包（backpack）把上限加倍并带走现有库存。

开火必须是原子的：action 生效之前检查 `ammo ≥ cost`，扣减、声音、火光全在成功分支里。打空时的规则是自动换枪，而且不需要为拳头写特判：从最强武器往下扫"已拥有且付得起一发"的武器，拳头排在表底、它的 ammo 列是"无需弹药"，hasAmmo 恒真——"打空自动切回拳头"不是规则，是表结构的推论。扫空的情况（拳头默认必持有，所以实际到不了）留给一声空枪音效即可。

另一个值得单独讲的设计：**丢掉武器的正确形状**。武器的老家在世界而不是玩家背包——地上捡起的霰弹枪就是一个带 doomednum=2001、打了 MF_SPECIAL 标记（可拾取）的 mobj。所以"丢弃"的实现不该给玩家加字段，而是在脚下 spawn 同类型的道具 mobj，让它走同一条拾取路径。进和出走同一扇门，武器因此不需要第二套身份。当前实现在玩家死亡时只清空双手、尚未把武器落成道具（单人语义），但形状已经留好：补这一条只是补一个 spawn 调用。

## 13.4 hitscan：同一条射线，回答两种问题

"这个怪物看得见我吗"和"我这一枪打中它没有"应该是同一个几何过程：一条射线（原点、角度、斜率）扫过地图，沿途只有两种事件——穿过一条线定义（linedef），或擦过一个物件。原版把两者建在同一个区块图（blockmap）遍历上；当前实现把它写成两个同形的函数（视线检查 / 线攻击），共享的判定规则是同一套垂直测试：

| 判定 | 回答的问题 | 形式 |
|---|---|---|
| 射线在每个相交距离的高度 | 子弹走到这条线时，飞在多高 | `z(t) = z0 + slope·t` |
| 开口（opening） | 这个高度能不能穿过这条线 | 双向线：`z(t) ∈ [两侧地板取大, 两侧天花板取小]` |
| 身体高度区间 | 这个高度落在不在目标的躯干上 | `z(t) ∈ [z, z+height]` |
| 平面半径 | 射线离目标中心够不够近 | `|dx| ≤ r, |dy| ≤ r`（按盒子，不按圆） |

单向线直接挡住一切；双向线看开口——开了一半的门，对低射的子弹是墙，对高射的子弹是空气。墙的相交距离和物件的相交距离各取最近，谁小谁赢：先打到物件 → 溅血（无血目标则火星）→ 走伤害管线；先撞墙或出了射程 → 在墙上冒火星。射线长度取 2048 单位（约 64 格），近战共用同一条 routine，只是把长度换成 64。

**auto-aim 是"没有垂直视角"的诚实答案。**DOOM 没有鼠标俯仰，弹道高度只能由游戏算：开火前先在眼睛高度打一条水平射线，在射程内找最近的可射击物件，令 `slope = (目标身体中心高度 − 眼高) / 距离`。瞄准自动了，但完全可预测——玩家很快学会"能瞄 = 它在我前方且高度差在视平线扫得到的区间里"。代价同样真实：怪物站在矮墙后、而你从视觉上看得见它时，水平视线的 auto-aim 可能取不到 slope（它的躯干区间不含你的眼高），子弹就平飞过去——**你打不到你看得见的那个目标**。而本实现为了简单，连瞄准 pass 都不查线，甚至能锁定墙后的怪物：真正的攻击射线会停在墙上，只剩一撮火星。这些都是明码标价的简化，不是隐藏缺陷。

## 13.5 抛射物：出生就带斜率的思考者（thinker）

火箭、等离子球、男爵的火球，都是打了 MF_MISSILE 标记的 mobj，发射时把角度和 slope 分解成动量：

```text
momx = cos(angle)·speed;  momy = sin(angle)·speed;  momz = slope·speed
```

之后每 tic：按 MAXMOVE 分步移动 + 区块图遍历查碰撞；撞上一个 solid 物件的判定还是那三条——我的 `[z, z+height]` 与它的 `[z, z+height]` 有交叠，且 |dx|、|dy| 不超过半径和。命中生物 → 伤害记给发射者、自己进爆炸状态；撞墙或触到地板/天花板 → 原地爆炸。抛射物撞墙不许滑动（第九章的滑动规则只留给玩家和怪物）——否则一枚火箭会沿着墙爬进你怀里才炸。

半径伤害只有一条减法：`实际伤害 = 基础伤害 − (平面近似距离 − 目标半径)`，下限为 0，作用范围固定 128 单位。距离用 AproxDistance（`|dx|+|dy|−大者的一半`，免开方，误差约 22%）。这条线性衰减解释了两种体验：贴脸的火箭几乎全额伤害，是同归于尽的武器；男爵火球在大厅尽头炸开时距离已吃掉大半个伤害，只是一记擦伤。hitscan 没有衰减、爆炸有衰减——这两条伤害通路的道德观不同，怪物的站位和玩家的战术都从这里长出来。

## 13.6 伤害与护甲：两个池子，一个计时数组

玩家的护甲不是一个数：绿甲、蓝甲各占一个点数池，再加一个"当前生效类型"。吸收比例不同——生效池替玩家挡下伤害的 1/3（绿）或 1/2（蓝），余下的进身体；池子不够就把剩余点数全部交出去，然后类型标记**塌缩**到还有点的池（绿 → 蓝 → 无）。蓝甲耗尽的一瞬，若绿甲点数还有存货，玩家立刻改用绿的比例。最常见的护甲 bug 就是漏掉塌缩：蓝甲打空后玩家还享受蓝的比例，穿着幽灵甲。

增益（power-up）更简单：一个 `powers[NUMPOWERS]` 数组，每格要么是剩余 tic 数，要么是布尔标记；玩家思考函数每 tic 把所有大于 0 的条目减一，**但跳过两个永久项**（strength 与地图显示）。永久项的值是 1，不是 3500——把它们一起递减，增益会在一百秒后无声消失。"一个数组 + 两个例外"是 buff 系统的标准形状；它的警告是：状态一旦存进表外数组，就必须同步进存档和跨关携带清单——第 15 章会讲漏掉这一课的直接代价。

伤害管线其余的步骤依次是：无敌检查（整个伤害作废）→ 护甲 → 身体 → 受击概率（随机命中则进 pain 状态，打断动作）→ 击退（`推力 = 伤害·常数/体重`，按源→目标方向分解进动量）→ 死亡判定：血量低于 −出生血量且有超死状（xdeath）则碎尸，否则普通死亡。击杀计数只记给玩家阵营，而且**记在死亡现场**——结算百分比的分子必须在扣血判死的地方产生，不能事后统计。

## 13.7 拾取：一张 keyed 在编号上的表

拾取逻辑 = 一个大 switch，键是地图物件的编号（doomednum）：2014 医疗包加 1 点血（上限 200），2013 灵魂之球直接顶到 200，2001 霰弹枪加 8 发枪弹。没有元数据、没有策略模式，表即规格——地图给你的就是这个数。

让道具"活着"的是两条规则：

1. **不能被消耗的物品，绝不能消失。**弹药满了，addAmmo 返回"没拿"，道具留在原地。先删再想效果，等于当众销毁玩家的库存——他的感知是游戏吞了东西。
2. **被消耗却毫无效果，比不让人捡更糟。**以狂乱包为例：满血时补血量为无效，但若因此"不给吃"，道具每个 tic 重新触发、重新播放拾取音效——地板上多了一只永远在嚎的罐头。原版的决定是无条件消耗：力量标记的写入是幂等的，所以满血吃下它仍有永久增益，"消耗"对得上"效果"。

两条规则的边界：**消耗必须造成玩家状态上持久或至少一次性的变化，否则拒绝消耗。**还有一个容易踩两次的坑：血量写了两份（玩家字段给 HUD，mobj 字段给命中判定），漏同步任何一份都会得到"HUD 显示 100 血、一发就死"的双面人。

## 13.8 状态条：第二块渲染目标

320×200 屏幕的底部 32 行不是 3D 视图的附属，而是一块完全独立的渲染面：先整张贴图（patch）STBAR 打底，再把动态元素逐个 blit 上去。数字不是字体而是十个 digit patch（STTNUM0..9，右对齐逐位叠加，需要百分号再叠一个 STTPRCNT）；脸是 patch——原版用一组脸图编码三个维度：血量十档、受击强度、转身角度（玩家转视角时脸跟着看）；当前实现只画一张静态脸，这是明说的简化。钥匙是 3 个比特拼出的 8 张组合图，贴一张就完。全程没有矢量字体、没有布局引擎，透明就是跳过那个颜色索引。

让人意外的一件事：**HUD 是最容易出厂"自动化测试看不见"的 bug 的地方。**测试断言 `ammo[CLIP] == 49`——真；但画出来的数字锚点偏了 10 像素，或者 Freedoom 的 STBAR 第三格标签是 FRAGS 而数字仍按原版 ARMS 的坐标画——测试一路绿灯，玩家看到的却是贴在错误标签上的数字。所以 HUD 的验证只有一步：headless 渲染一张含状态条的完整 BMP，转成 PNG，**用眼睛看**。这一步不丢人：渲染对象的裁判就是眼睛，眼睛只需要每次改动后工作一次（这套"没有人的视觉验证"机器，第 16 章完整展开）。

## 这样做的代价 / 放弃了什么

- hitscan 不检查地板和天花板：对着地面开枪，射线会从地板下继续穿出去，够得着隔壁房间的怪物；不存在"贴地滚出去的弹道"。
- auto-aim 的瞄准 pass 不查线：可能锁定墙后的怪物，最终只回馈一撮火星。
- BFG 简化为命中即径向爆炸，没有原版那颗沿途吃伤害的 tracer 球。
- 枪口火光不带动态光照（A_Light1/2 是空函数）：会响，不会照亮世界。
- 脸静态；切枪动画只有帧变化、没有位移；无拾取消息；死亡暂不掉落武器道具。

这些简化共享同一个标准：**只动数值，不动判定结构。**五状态机与 pending 握手、一条射线两种问题、四条垂直测试、带塌缩的两池护甲、"不可消耗必留存"的拾取规则——这些是战斗感与信任感的骨架。数值随时可以调回来；骨架错了，玩家三秒钟就退出。

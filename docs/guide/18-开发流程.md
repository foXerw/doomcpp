# 18 开发流程：这个项目是怎么被推进的

## 为什么需要这一章

前面 17 章讲"怎么实现"，但真正让这个项目走到今天的不是实现能力，而是**推进方式**：
一个复刻项目的时间尺度是月而不是小时，而它的每一步都同时存在三个诱惑——
抄原版源码（最快）、凭记忆猜语义（最省事）、宣称完成（最好看）。
这一章记录用来对抗这三者的流程，以及流程本身犯过的错。

## 一个里程碑的形状

每个里程碑（P0…P18）都走同一条流水线，六个阶段，缺一不可：

```
① 目标文档（spec）   →  ② 实现计划（plan）  →  ③ 逐任务红-绿提交
        ↓                                            ↓
⑥ 记忆/README 更新  ←  ⑤ 合并 + 打 tag  ←  ④ 全量验收（gate）
```

### ① spec：先写"做到什么算做完"，再写怎么做

`docs/superpowers/specs/` 里每份文档的固定内容：范围、**范围内/范围外**、
保真标尺（哪些数值必须忠实、哪些允许本地标定）、验收判据。

"范围外"这一节是真正起作用的部分。P6a 的 spec 明写了
"挤压伤害、怪物使用开关、关卡切换"不在范围内——于是后面每一次
"要不要顺手也做了"都有据可依，不至于把三个里程碑糊成一团。

spec 也允许被推翻。`2026-07-25-roadmap-realignment-design.md` 整份文档就是
"重新对齐"：把"渲染也必须定点"的标尺**下调**，把 P8 联机移出正式路线图。
下调的理由不是懒，是第 17 章记的那次失败：定点回填让坑底空洞从 65 涨到两万五，
根因定位不动。**标尺必须能被证据修改，否则它只是愿望。**

### ② plan：把 spec 切成"一次能红一次能绿"的任务

`docs/superpowers/plans/` 每份计划的任务粒度是判据：
一个任务 = 一个可独立验收的交付物 + 它自己的测试 + 一次提交。
"实现渲染器"不是任务；"让平面带按 opening 收边，并让覆盖计数为零"才是。

计划文档里还有一节叫 **Review Focus**：列出"这个阶段的测试覆盖不到、
但玩家一定会撞上"的失败模式。P8 那份列了五条，其中两条后来直接变成了必修项
（姿态必须证明在真实空间内；special 语义必须被地图反证）。
这一节的作用是**在动手之前把怀疑写下来**，免得事后用"看起来没问题"糊过去。

### ③ 红-绿提交：每个功能先有一个失败的测试

顺序不可调换：先写测试 → 跑出红色 → 实现 → 变绿 → 提交。
理由很朴素：没有红过，你不知道这条测试能不能失败（第 16 章的负控）。

提交信息的写法有规矩：**说清"为什么"而不是"改了什么"**。
`fix(render): close visplane bands against the opening, not nominal heights`
之后跟着的是失败现象、被否证的假设、以及验证数字。
半年后 git log 是唯一还活着的文档，测试代码只说明"现在怎样"。

### ④ 全量验收：七道 gate，每次合并前全绿

```
ctest = 单元/逻辑测试 + runtime_smoke + ai_smoke + campaign_smoke + sound_smoke
                       + render_audit + clip_audit + asset_audit
```

规则：**gate 必须能失败**（负控验证过），**不能失败的 gate 比没有 gate 更糟**。
这条规矩是被现实教出来的：asset_audit 的"单面墙关键失败"判定读错了自己写的
字符串第几个字节，于是它永远输出 0、永远绿——一个已经坏掉的守门人。

### ⑤ 合并与打 tag

```bash
git checkout main
git merge --no-ff feat/pN-...        # 保留分支形状，历史里看得见里程碑边界
git tag -a vN.M-<slug> -m "..."      # tag 指向合并提交，不指向分支尖端
```

`--no-ff` 不是洁癖：复刻项目会反复出现"当时以为做完了，后来发现漏了"，
合并提交让"这一轮的范围"在图上是一个可回看的节点。

### ⑥ 记忆与 README：把结论写给"下一次的自己"

README 的 Roadmap 与 Known limitations 是**同一轮工作的产物**，不是事后补的。
每条限制必须写清楚是"没做"还是"做了但简化"，以及为什么。
跨会话的记忆文件里存的是**判断和教训**（哪个假设被否证、哪个方案被放弃及其代价），
代码结构和已修复的 bug 不存——那些 git 已经记着。

## 分支与仓库约定

| 约定 | 值 |
|---|---|
| 稳定分支 | `main`，只接受 `--no-ff` 合并 |
| 阶段分支 | `feat/pN-<slug>`，一个里程碑一条 |
| 修 bug 分支 | `fix/<slug>`（如 P3.5d 的渲染覆盖修复） |
| tag | `vN.M-<slug>`，只打里程碑，不打提交 |
| 资产 | `assets/*.wad` **不入库**（GPL 与体积），体检工具在缺 WAD 时自动跳过对应 gate |
| 提交语言 | 代码与提交信息英文，文档与注释中文（术语表见第 00 章） |

## 流程失败的样子（本项目真实发生过）

流程不是只用来成功的，下面三条是它失败的记录：

1. **P9 的提交直接落在了 main 上。** 合并 P8 之后顺手 `git checkout main`，
   后续工作就一路提交在主干，分支形同虚设，`--no-ff` 的里程碑边界消失了。
   根因是"合并"被当成了阶段的终点动作而不是阶段的一部分。
   对策：合并之后**立刻切回阶段分支**，或者在合并前把收尾提交做完。
2. **文档先引用了不存在的 tag。** P9 的结论文档写着 `v0.16-p9-later-levels`，
   而 tag 那时还没打。这类"文档跑在事实前面"的错误在体检工具的输出里也一样出现过
   （探针脚本中途崩溃，却已经把"tag 不存在"写进了结论）。
   对策：任何"已交付"的陈述，写之前用一条命令验证它。
3. **一次修 bug 引出了更严重的 bug。** P8c 加 power-up 时，跨关携带清单漏了
   `powers[]`，于是每过一关无敌/狂暴/背包全部消失——测试全绿，因为没有任何测试
   走过一次关卡切换。独立 review 才抓出来。
   对策：**新增状态字段时，先搜"谁复制这个结构体"**；复制体的地方（carry、save）
   必须同步，并且要有跨关测试钉住它。

## 什么时候该停下这条流程

流程的成本是真实的：一份 spec + 一份 plan + 七道 gate + 一次独立 review，
比"直接把功能写完"贵好几倍。它划算的前提是——

- 你会**回来改**（复刻项目必然回来改）；
- 你有**不能靠眼睛发现的错误**（1 像素的缝、静默不生成的钥匙、永远为绿的 gate）；
- 有**第二个大脑**参与（人或 AI agent），它没有你脑子里的隐性前提。

三条都不成立时，直接写代码更诚实。这本书的立场是：渲染、碰撞、关卡机关三条都成立，
所以流程不是官僚，是**把"我记得为什么"外包给机器**。

## 这样做的代价 / 放弃了什么

- **慢。** 一个看起来两小时能做完的改动，加上测试、负控、文档和 review，实际占一晚。
  换来的是第二天不必花两晚查为什么门打不开。
- **文档会过期。** spec 里的"范围外"清单会被后来者违反；plan 的复选框只有当时有意义。
  所以真正维护的是 README 的限制清单和记忆文件，其余作为**决策现场**保留，不追求同步。
- **流程会掩盖判断力的缺失。** 一份写得很漂亮的 plan 如果建立在一个错误的保真标尺上，
  只会让错误被更彻底地执行。第 17 章那次定点回填就是这种情况：流程完整、提交干净、
  结论是错的。能救它的只有"允许下调标尺"这一步。

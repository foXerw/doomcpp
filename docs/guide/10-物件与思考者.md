# 10 · 物件与思考者

> 地图物件（mobj）是玩家、怪物、火箭弹、药包、尸体、一盏台灯的统称。它们共用一张状态表、一条思考者（thinker）链表和一套物理。本章讲这三样怎么组装，以及组装错了会掉进哪三类坑。

## 不做这件事会怎样

- 火球僵尸每一 tic 喷一发火球——攻击动作被当成了每帧回调，35 发/秒，玩家瞬间蒸发。
- 火箭弹爆炸杀死了一只 imp，imp 的死亡动作又炸了别的什么——链表在遍历中被改了结构，游戏随机崩溃或跳过某些物件的思考。
- 读档之后，怪物忘记了打它的仇人，追踪弹直着飞进墙里——指针字段没有跟着对象一起活过来。
- 新生成的血渍掉到 z=0 不消失，因为它出生时没人告诉它地板在多高。
- 火球贴着墙滑行就是不炸——给玩家用的滑动规则被无差别套用到了抛射物上。

## mobj 的三个面

一个 mobj 同时是三样东西，字段按面归类：

| 面 | 字段 | 谁读写 |
|---|---|---|
| 状态机 | state 指针、tics 剩余、target | 状态表（只读）与 thinker |
| 物理 | x/y/z、momx/momy/momz、floorz/ceilingz/dropoffz、flags | 第 09 章的移动代码 |
| 空间在场 | subsector、sprite/frame/fullbright/light | 渲染器（只读缓存） |

第三行值得停一下：**渲染缓存**。`P_SetMobjState` 在进入状态时把精灵名和帧号拷进物件本体，渲染器每帧只读这份拷贝，从不回头查状态表。渲染热路径与逻辑解耦，这是第 08 章"按 subsector 收物件"能吃干净的原因。

## 状态表是一张只读数据表

```text
state_t { sprite, frame,        # frame 的 bit15 = 全亮位（火光、plasma 球）
          tics,   nextstate, action }
```

`tics = -1` 的含义是**停留**，不是"零时间"：装饰、拾取物、道具的静态状态全用 -1，物件永远不会自己推进；`nextstate = 自身` 配合 -1 表达"永久"。静态物件（台灯）和会思考的物件（怪物待机的 A/B 帧循环）共用同一张表，差别只在行内容——引擎不需要"装饰系统"这个独立模块。

## 动作在状态入口派发，不在每 tic 派发

```text
P_SetMobjState(mo, s):
    mo.state = states[s];  mo.tics = states[s].tics
    刷新渲染缓存
    调用 states[s].action              # ← 动作只在这里跑一次

P_MobjThinker(mo):                    # 每 tic
    跑物理（第 09 章）
    if state.tics != -1 and --mo.tics == 0:
        P_SetMobjState(mo, state.nextstate)
```

这个边界就是那类"火球机关枪"bug 的防线：动作属于**转移**，tic 递减属于**驻留**。反过来的错误同样真实——如果你把每 tic 都要跑的逻辑（比如 A_Look 环视）写进 thinker 的主体而不是挂在待机状态上，玩家专属逻辑和怪物逻辑就会在同一函数里打架。原版的组织方式是：待机状态行 10 tic、下一帧行再 10 tic，入口派发天然就是节流阀。

## 遍历中删除：延迟移除模式

思考者链表的致命性在于：**状态动作可以在遍历进行中杀死并删除任何物件**——爆炸链式引爆油桶，油桶又炸死正在被迭代的怪物。

```text
P_RunThinkers():
    thinkering = true
    for it in mobjs:                  # 预取 next 再处理
        if not it.removePending: P_MobjThinker(*it)
    thinkering = false
    mobjs.remove_if(removePending)    # 一趟 pass 结束后统一摘除
```

删除请求（`P_RemoveMobj`）在 pass 中只挂标记，pass 外才真摘节点。容器选择由此决定：

- `std::list`（doomcpp 的选择）：节点地址稳定，摘除一个不影响其余指针有效性，代价是遍历局部性差。
- 对象池 + 代数句柄（index + generation）：局部性好，但要求**所有**互相引用的字段存句柄不存裸指针。
- `std::vector<mobj_t>` 直接装对象：最差——`push_back` 扩容重分配会让所有 target/来源指针一夜作废，而且这类崩溃离写下它的那行代码很远，属于最恶毒的 bug 形态。

判据：**只要物件之间允许互相持有引用，容器就必须保证节点地址稳定，或者根本禁止持有地址。**

## 指针的重生：index-then-repair

同一套"不能持有裸地址"的逻辑延伸到存档。怪物记着"打我的那个人"，这个引用必须穿越写盘/读盘或任何 compact 存活。通行模式两步走：

```text
存：target 写成"它在链表里的序号"（找不到 = -1）
读：第一趟把所有 mobj 建出来；
    第二趟拿序号数组回填 target = revived[i]
```

第二趟不可省：读档第一趟进行中，序号 5 的物件可能还没出生。纪律是：**以后每加一个指针字段（tracer、源子弹、仇恨记忆），存档格式里就要有对应的序号字段**，否则读档后它静默变 null——症状是"读档后怪物不再内讧"，这种 bug 没有任何测试会红。

## 出生即播种

新物件的 floorz/ceilingz/z 必须在**第一个物理 tic 之前**是诚实的：

```text
P_SpawnMobj(x, y, z, type):
    由 BSP 求 subsector → 扇区
    floorz/ceilingz = 扇区高度；z 钳进 [floorz, ceilingz-height]
```

否则血渍带着 0 号地板出生、往地底坠 35 秒；抛射物出生在发射者盒子里会被 thing 判定永远阻挡自己（解法：从身前 32 单位处出生）。天花板钳制还有一条防退化规则：`ceilingz - height` 若低于 floorz（超薄扇区、运动中的门），取 floorz——**天花板永远不许把物件压到自家地板以下**，这条在第 11 章的压顶机关里再次出现。

## 飞、浮、重力

| 组合 | 典型 | 行为 |
|---|---|---|
| 默认（落地怪） | 僵尸、男爵 | 无 MF_NOGRAVITY 时吃重力；z 跟随支撑面（第 09 章） |
| MF_NOGRAVITY | 玩家、抛射物、大部分特效 | 垂直动量只在显式给出时存在 |
| MF_FLOAT | 亡魂、红魔 | 不落地：出生时悬在地板 +24 处，飞行时由天花板钳制兜底（同样不许压穿自家地板） |

## 抛射物也是 thinker

发射 = 生成物件 + 按斜率给动量：

```text
speed = info.speed                       # 单位/tic
momx/momy = speed × (cos, sin)(朝向)
slope = (目标中心z - 出口z) / 水平距离
momz = speed × slope
```

判定规则一条：**碰墙即爆**。位置本 tic 没有任何变化（被彻底阻挡）、垂直撞到地板/天花板、或盒子碰到可伤害目标——都直接进入爆炸状态。抛射物**不许滑动**：玩家的滑动是手感，抛射物的滑动是 bug——绕墙的火箭弹会把范围伤害的平衡全部作废，而且它从数学上说不清"什么时候才算撞墙"。

## radius / height / mass：击退公式

击退冲量沿"来源→受击者"方向，大小：

```text
thrust = damage × (1/8) × 100 / mass     # 定点：damage × (FRACUNIT>>3) × 100 / mass
```

mass 是 mobjinfo 的一列：木桶 100、重装兵 1000。同一发火箭，木桶被炸飞撞墙（还能连锁），男爵只是晃一下——"油桶是好武器"这个玩法，是这一行公式给的。radius 和 height 同样按物件给：方盒随物件变宽变小（亡魂盒子窄、红魔盒子高），第 09 章的所有判定对一切物件同构，没有玩家特例。

## 状态表的生成问题

几百行状态表，手抄必错。当表大到这个量级，正确姿势是**从参考数据文件（反编译产物/社区规范）用脚本生成**，然后补上生成解决不了的那一半——验证：

```text
static_assert(states 行数 == 预期)        # 缺行、多行：编译期爆炸
for 每一行: nextstate < 行数              # 悬空转移：启动自检
for 每个 mobjinfo: 五个状态索引的 sprite 与自身一致
```

生成消灭**转录错误**，验证消灭**参考本身错位**（参考文件行序和你的枚举差一位是真实事故）。两者都要，缺一不可。

## 这样做的代价 / 放弃了什么

- **延迟移除**让物件在"逻辑上已死、物理上还在"的状态里多活半趟 pass：同一 pass 内后遇到的检查必须自己防（doomcpp 的每个迭代都查 `removePending`）。这是用一致性换稳定性的明码交易。
- **入口派发**意味着任何"每 tic 都要跑一点"的逻辑都得伪装成一个循环状态（nextstate=自身），表会变长；换来的是动画即节流、行为即数据。
- **链表/池**放弃了 vector 的缓存友好与随机访问；渲染器每帧按 subsector 重新收集物件，付出 O(n) 重建，换掉整个 blockmap-thing 维护体系（第 12 章会看到这比它省下的多）。
- **脚本生成 + 编译期断言**把"改一行表"变成"改一个数据文件再重新生成"，调试时多一步；但表有几百行时，这是唯一能睡着觉的做法。

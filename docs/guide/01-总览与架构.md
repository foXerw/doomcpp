# 01 总览与架构

## 不做这件事会怎样

一个能跑起来的 DOOM 引擎有好几种写法，但只有一种在三个月后还改得动。

**第一种是"一坨"**：一个 main 文件，全局变量到处飞，渲染函数顺手改一下玩家位置，碰撞函数顺手往画面里画两笔。第一天它最省事，第七天你会遇到这样的 bug：按了开关之后门的高度确实对了，可画面里的门纹丝不动；你把渲染端的取值改成"实时读一份"，于是同一帧里门的上下两半用了两个不同的高度。这类 bug 无法靠读代码定位，因为"这份状态归谁所有"在代码里根本没有答案——它有两个答案，而两个都在跑。

**第二种是"模块划清了，但打在一个可执行文件里"**。看起来清楚了，代价是**验证变贵**：任何一条想检查世界状态的测试，都得先开窗口、初始化图形与音频、把字体和调色板准备好。于是不出意料地，你只写了三条测试；于是"这一帧画对了吗"重新退化成靠肉眼盯着屏幕。

**第三种是这本书要讲的：先划边界，再写算法。** 边界不是审美问题，它决定你能不能廉价地问出一个问题——让逻辑自己跑，画面另说。

## 一帧里到底发生了什么

DOOM 的时间不是连续的，它被切成 **tic（逻辑帧）**，1 tic = 1/35 秒。渲染帧率和逻辑频率是两件事：一帧画面可能紧跟在 0 个、1 个或多个 tic 之后。整帧的数据流是单向的：

```
主循环（每一轮）:
    1  采集输入          把设备事件攒成一份 ticcmd（前后.move、左右.move、转向、使用/攻击键）
    2  推进逻辑          while (到了该跑的 tic):
                           P_RunTic():
                               for t in thinker 链表:  t.Tic()   // 玩家、怪物、门、电梯、抛射物、火焰
                               状态机推进            // mobj 的 state 走完计时器就换下一个 state
                               关卡计时器 +1         // 贴图动画、闪烁灯光、门延迟都读它
    3  生成画面          R_RenderPlayerView(viewz, angle, x, y):
                           BSP 前序遍历 → 屏幕列的裁剪区间
                             → 墙（列贴图）→ 地板/天花板（visplane）→ 精灵（vissprite）
                           状态条 HUD 叠加
    4  呈现与混音        把 320×200 交给窗口；音频在自己的线程里按已排好的事件播放
```

三条不可动摇的规则：

1. **只有第 2 步能写世界。** 第 3 步是纯读，读到的是某个 tic 结束后的快照。
2. **第 2 步不许知道屏幕。** 逻辑里没有"玩家看到的"这种概念，只有"世界是这样的"。
3. **第 4 步不许反馈进第 2 步。** 呈现的快慢不能改变模拟的快慢，否则同一份存档在不同机器上会长出不同的关卡。

## 模块边界

| 模块 | 装什么 | 允许依赖 | 为什么这么切 |
|---|---|---|---|
| 核心数学 | 16.16 定点、BAM 角、三角表、查表随机数 | 无 | 它被所有人用，所以它不能用任何人 |
| WAD 读取 | 容器目录、lump 缓存 | 核心数学 | 只有文件 I/O，没有游戏语义 |
| 地图数据 | 九种 lump 的解析、区块图、seg→扇区派生 | 核心数学、WAD | 静态数据，加载后只读 |
| 玩法 | 碰撞与移动、思考者与状态机、机关、AI、战斗、流程、存档 | 上面三个 | **整块不许链接图形或音频** |
| 渲染 | BSP 遍历、墙列、可视平面、精灵、调色与拼装 | 核心数学、WAD、地图数据、静态物件表 | 只读世界，只写 framebuffer |
| 平台 | 窗口、输入、混音 | 第三方图形/音频库 | 全工程唯一允许碰第三方库的地方 |
| 界面 | 状态条、字体、标题、结算 | 渲染 | 它是"另一种画面"，不是另一种逻辑 |

依赖只能是单向的一张 DAG，画出来就是全部规矩：

```
        核心数学
       ↑    ↑    ↑
   WAD  地图数据  静态物件表
       ↑    ↑    ↑
       └── 玩法 ──┐        ← 只有这一层写世界
            渲染 ←┘        ← 只读世界，只写 framebuffer
             界面          ← 状态条/字体，也是渲染的一种
   =======================  链接边界：以上进一个静态库，以下单独成库
            平台           ← 唯一允许出现第三方图形/音频头文件的地方
             可执行体
```

把"核心数学 + WAD + 地图数据 + 玩法 + 渲染 + 界面"编译成一个**静态库**，把平台层单独编译，测试程序只链接前者。这件事的效果远超它的成本：

- 单元测试可以直接调用真的 `P_TryMove`、真的门 thinker、真的命中判定，不需要窗口、不需要资产目录、不需要人工点击。
- 审计工具（`--gapscan`、`--dumpframe`、`--smoketest`）用的就是同一份库、同一条初始化路径，只是换了命令行。它们和发布版之间没有"测试专用替身"，所以不会出现"测试绿、真机坏"。
- 最值钱的一条是**链接器替你守规矩**。如果你想在玩法里图省事查一下"这个像素在屏幕上第几列"，编译会直接失败。这个失败比任何一条代码评审都可靠，而它逼你想出的替代方案（把需要的信息作为世界状态的一个字段存起来）通常才是对的设计。

反过来说，一旦"渲染可以写世界"这个口子打开，上面三条规则就全废了——你会得到一个只有在窗口开着、只有在你这台机器上才能观察的引擎。

## 这本书说的"忠实"是什么

只说一次，后面不再讨论：

> 复刻的是**设计**——数据结构、算法流程、数值表示、手感。
> 不复刻字节，也不把原版的 C 翻译成 C++。

要复刻的三样：地图用同一组数据结构（因为关卡数据就是按它排的）；可见性与碰撞用同一套算法流程（因为它们是关卡设计的隐含前提）；位置和角度用同一套数值表示（因为它们决定手感，也决定确定性）。

不要求的两样：像素逐字节一致（没有参考引擎时，这个目标无法验证；一个无法验证的目标不是目标，是一种信仰）；与原版源码逐行同构（原版里既有设计也有 1993 年的妥协，两者混在一起，照抄会把妥协当设计供起来）。

当"原版这里到底怎么算的"从手上的数据判不出来时，本书的规则是：**选一个自洽且能被机器检查的行为，在注释里写明这是本地标定，不声称与原版逐值一致。** 这不是偷懒，这是把"可验证"放在"可声称"之前的工程纪律。

## 里程碑的形状

顺序如下，每一步的产物都必须能**被观察到**——不是"编译通过"，而是"有一个此前无法回答的问题现在能自动回答了"。

| # | 步骤 | 新打开的判据 | 失败时长什么样 |
|---|---|---|---|
| 1 | 读通 WAD | 目录、lump 尺寸、名字查找全部可断言 | 找同名 lump 找到错的；标记 lump 被当数据读 |
| 2 | 解析一张地图 | 顶点数/扇区数/某条门的两侧扇区可逐条断言 | 记录步长算错一个字节，整张图错位 |
| 3 | 画出实心墙 | 第一次能"看一眼就判断对错"：轮廓 | 天空与墙混色；远处墙在错误高度收口 |
| 4 | 贴上纹理 | 贴图名→像素可断言，U/V 可断言 | 纹理左右镜像；门开一半时贴图跟着地板掉 |
| 5 | 地板与天花板 | 首次能检查"该被盖住的格子有没有被盖住" | 坑洞、平面互相穿透 |
| 6 | 碰撞与移动 | 首次能 headless 跑一段"人走一条路线"的断言 | 穿墙；下台阶悬空 |
| 7 | 精灵与遮挡 | 怪物出现在正确位置、被正确遮挡 | 台阶后方的怪物整体消失 |
| 8 | 思考者与状态机 | 门的完整开- hold-关周期可跑可断言 | 删除正在遍历的物件导致崩溃 |
| 9 | 战斗 | 命中、伤害、拾取、死亡链可断言 | 护甲吸收算反；武器永远打空 |
| 10 | 关卡机关 | 首次要证明"地图可通关"，需要可达性诊断 | 按了开关没反应；门永远不开 |
| 11 | 敌人 AI | 首次要证明"从远处走过来"，需要路径统计 | 怪物对着墙原地转圈 |
| 12 | 战役流程 | 关卡序列、结算、统计可断言 | 打完最后一关没有结局 |
| 13 | 音频与存档 | 存档字节可回读比对 | 读档后关卡状态半新半旧 |
| 14 | 正确性扫荡 | 把前面所有"我以为没问题"变成常驻检查 | 上面每一步的漏网之鱼集中爆发 |

**为什么是这个顺序。** 一句话：先建立"世界是可读的"，再建立"世界是可见的"，最后才建立"世界是活的"。第 2 步早于第 3 步，是因为画面错了你无从下手，除非你能确定数据本身是对的。第 5 步早于第 6 步，是因为碰撞的判据（脚下高度、头顶高度）本来就来自渲染用的那套几何。第 8 步（思考者）故意排在第 7 步之后：门和怪物都是思考者，但先把"一帧画面能稳定复现"建立起来，你才有能力判断"一个状态机是不是每 8 tic 动了一次"。第 14 步不是收尾的附录，它是唯一能证明前 13 步没白做的事——把所有"不该发生"写成能跑的机器检查，见第 16 章。

## 这样做的代价 / 放弃了什么

- **跨模块的"顺手优化"变得不可能。** 渲染不能因为"反正逻辑那边算过"就直接借用一个临时值，一切共享必须显式进世界状态或显式传参。代价是样板代码和多一份上下文结构体；收益是每个值都有唯一主人。
- **启动时间被加载期换掉了。** 派生数据在加载时算完（第 04 章），意味着换关卡要付一次全量重建，而内存里同时存在"原始记录"和"派生视图"。
- **固定 35Hz 的逻辑频率意味着输入延迟最多 1 tic。** 想把它调高（更顺滑）就等于改变了所有以 tic 计时的数值：门的延迟、怪物的反应时间、子弹飞行距离，全部要重新标定。所以这本书不动它。
- **放弃 demo 兼容。** 不追求逐字节一致，就意味着不能声称"录下来的回放能在原版上播"。这是一个自觉的选择：你要的是自己的关卡在自己的引擎上表现正确，不是和 1993 年的录像带兼容。
- **放弃"照着原版抄就不许改"的心理保险。** 边界划清之后，你会不断遇到"原版这里其实可以更简单"的时刻，而你必须真的去做判断，而不是拿"原版就是这样"当挡箭牌。

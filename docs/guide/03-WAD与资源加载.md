# 03 WAD 与资源加载

## 不做这件事会怎样

资源层最容易犯的不是"解析不出来"，而是"解析出来了但取错了那份"。四种典型症状：

- **同名覆盖失效。** 你用 `map<名字, 索引>` 存目录，重名时保留第一个。于是替换贴图包（PWAD）里的新纹理永远不生效——不报错，只是画面"还是老样子"。
- **按尺寸猜类型。** `if (size == 4096) 当 flat 读`，于是某个恰好 4096 字节的补丁被当成 64×64 索引图，画面里出现半张脸或者随机色块。
- **拼装放在每帧。** 每列墙重新合成一次纹理。帧率掉到三分之一，而没有任何一处逻辑出错。
- **精灵装错了。** 你不知道 `POSSA2A8` 意味着"同一个 lump 装进两个朝向槽位、其中一个是镜像"，于是解码了两遍，或者把镜像装到错误的朝向上——怪物会"背对着你往前走"。

这四条都发生在"从字节到可绘制图像"的中间地带。把这一段做对，后面所有章节拿到的都是一块干净的 RGBA，不必再回头怀疑它。

## WAD 容器

```
文件头 12 字节:
    char[4]  magic        "IWAD" 或 "PWAD"
    int32    lumpcount
    int32    diroff       目录区起始偏移
目录项 16 字节 × lumpcount:
    int32    filepos
    int32    size
    char[8]  name         不保证以 NUL 结尾，尾部常补空格
```

只有这三个字段。**没有类型、没有版本、没有压缩标志**——一个 lump 是什么，完全由名字和上下文决定。这既是它的简单之处，也是上面第二个症状的来源。

### 名字不唯一，所以查找必须反向

目录里同名项可以有任意多个，而且这是**特性**。它存在的理由就是资源替换：IWAD 在前，PWAD 追加在后，查找时"最后出现者胜"，替换自动发生——补丁文件里不需要任何元数据。整套贴图包、关卡包、音乐包机制都建立在这一条加"反向扫描"上。

```
全局查找 name:
    for i = lumpcount-1 downto 0:
        if 相等且大小写无关(i.name, name): return i
    return -1                        // "check"版本；"get"版本找不到就致命错误

在两个标记之间查找 name:              // 地图、精灵、flat 都这么干
    a = 标记起点下标; b = 标记终点下标
    for i = b-1 downto a+1:
        if 相等(i.name, name): return i
```

标记（`S_START`/`S_END`、`F_START`/`F_END`）本身是 `size == 0` 的空 lump，既不是数据也不是缺失，而是区间边界。**把空 lump 当"还没缓存"处理**是另一个经典 bug：如果缓存判据写成"数据为空即未加载"，标记 lump 就会每次访问都重新读盘（读 0 字节，永远为空，永远重读）。加载状态要用一个显式的位，或者用"解出来的宽/高是否为 0"这类真正属于内容的判据。地图数据不在标记区间里，而是靠名字成组：`MAP01` 与 `E1M1` 两套方案，同一张图的九个块紧挨着出现（第 04 章）。

### 缓存一次性读，还是每次读

```
readLump(i):
    if loaded[i]: return cache[i]          // 返回引用或副本都行，但别返回进 vector 的裸指针
    cache[i] = 从 filepos 读 size 字节
    loaded[i] = true
    return cache[i]
```

原版的做法是"用到的 lump 常驻内存"（外加一层可回收的缓存分类）。对自写引擎这是正确的默认：一个 patch 可能被 4 张纹理引用，一张纹理可能被 200 面墙引用，而整个资源包通常只有十几 MB。**每次现读**只在一种情况下值得——超大资源包或嵌入式，那时改成"目录常驻 + 数据按需 + 上限淘汰"。但被淘汰的必须是你**派生出来的产物**（复合好的纹理、解好色的精灵），而不是原始 lump：原始 lump 很小，留着不亏，重算产物才贵。

## PLAYPAL：为什么是 14 套

```
PLAYPAL = 14 × 256 × 3 = 10752 字节（尺寸是死的，可当格式校验）
第 0 套 = 最亮；第 1..12 套是同一批颜色逐级压暗；第 13 套是全红色调（受伤闪红）
```

需要 14 套而不是"一套 + 运行时乘系数"，是因为 1993 年的显示器工作在**索引色**模式：每个像素存的是一个字节下标，你能改的只有"这张 256 色的表本身"。把"变暗"表达成"换一套表"，逐像素成本就只是一次数组读取。今天你已经没法靠改调色板影响屏幕了（framebuffer 是 RGBA），但"索引→索引"的查表保留了下来，它就是 **COLORMAP**：

```
COLORMAP = 34 张 256 字节的表，共 8704 字节
    第 0 张   恒等（全亮）
    第 1..32 张  32 级压暗
    第 33 张     全黑（不受光的特殊场合）

取色:
    档 = clamp((255 - sector.lightlevel) / 8, 0, 31)
    map = colormaps + (档 << 8)                 // 一张表 256 字节，所以是 <<8
    rgb = palette[ map[ texel索引 ] ]           // 两次读表，零算术
```

**这就是"距离衰减"（distance shading）的位置。** 原版在正常光照下并不让距离参与着色——景深全靠关卡作者给每个扇区填的 lightlevel；只有拾取强光的那几秒，亮度才随与玩家的距离变化，形成一圈以玩家为中心的辉光。一旦你改成运行时乘亮度（用 RGBA 之后几乎一定会这么改），加一层距离衰减几乎免费，观感也明显变好，但代价是**它不再有标准可比对**：线性还是平方、按视距还是按投影深度、天空要不要参与（不该，否则天空会随视角变暗）——全要用眼睛标定，而且要一直标下去。

## PNAMES + TEXTURE1 / TEXTURE2

一张"纹理"不是图像，是**配方**：一串带原点的补丁，合成成一张 64×128 之类的 bitmap。

```
PNAMES:   int32 count;  count × char[8]          // 补丁名表；纹理用下标引用它
TEXTURE1 / TEXTURE2:
    int32 numtextures; int32 offsets[numtextures] // 每张纹理的块内偏移
  纹理定义 22 字节头 + 8 字节/补丁:
    uint16 width, height, patchcount, pad
    { int16 originx, originy, patch, bintile, bwidth, bheight } × patchcount
```

`patch` 是 PNAMES 的下标而不是 lump 号——多这一层间接，是为了让替换发生在名字层（见上一节的反向查找）。为什么要 `TEXTURE1` **和** `TEXTURE2`：一张表放不下所有纹理。所以两张都要读、都追加进同一张运行时纹理表，**纹理号 = 拼接后的序号**。忘记读 TEXTURE2 的症状很特别：大部分墙正常，少数几张是白块。

```
composite(定义, 补丁表):
    dst = 全 0 的 width×height（alpha 0 = 未画）
    for mp in 定义的 patches:
        p = 补丁[mp.patch]
        for y in 0..p.height-1:
            for x in 0..p.width-1:
                sx = (mp.originx + x) mod width       // 水平环绕：纹理是横向平铺的
                sy = mp.originy + y
                if 0 <= sy < height 且 p[x][y] 已画:   // 后画的补丁盖住先画的
                    dst[sy][sx] = p[x][y]
    return dst
```

`originx/originy` 可以为负（补丁从纹理左上角外面开始），所以两次边界检查不能省。补丁之间的叠放顺序就是数组顺序，这是关卡作者"贴出一面复杂墙"的唯一手段。

### 补丁格式：列优先的 post 游程

```
头 16 字节: int32 width, height, leftoffset, topoffset
           int32 column directory[width]  （每个是"该列数据相对列区起点的偏移"）
列数据（每列独立）:
    loop:
        topdelta = read u8
        if topdelta == 0xFF: break        // 终止符，不是行号
        length   = read u8
        pixels   = read u8 × length       // 调色板索引
        行 = 累计 topdelta                // 关键：topdelta 是"相对上一次 post 的增量"
        把 pixels 写入 行..行+length-1
```

两个必须说清的细节。**`topdelta` 是相对量、逐 post 累加**，不是绝对行号——当绝对行号读，图形每一段都会挤到顶部。**`0xFF` 是终止符而不是行号**，所以"从第 255 行开始的 post"表达不出来，这是格式自身的极限，也是为什么必须"先判终止符再累加"。第三个咬人处：有些 WAD 的 post 会越过补丁底边，写入前不逐像素裁剪就是堆越界——症状是偶发崩溃而不是画面错误，极难归因。

**`leftoffset` / `topoffset` 是锚点**：把补丁的第 `leftoffset` 列、第 `topoffset` 行放到基准位置，面定义的 `textureoffset`/`rowoffset` 在此之上再加。多数工具把两者写成宽高的一半，于是"不指定偏移时贴图中心对准基准点"。忽略它们不会报错，只会让同一张图在不同来源的 WAD 里对不齐——"纹理偏了半张"的第一嫌疑人。

## Flats：4096 字节，什么头都没有

```
flat = 64 × 64 个调色板索引，行优先，4096 字节，无宽度字段、无魔数、无压缩
正确判据 = (位于 F_START..F_END 区间内) && size == 4096 && 名字 != "F_SKY1"
```

64×64 是硬约定，而且是**设计**不是巧合：平面纹理映射因此只用位运算取坐标——`索引 = (x & 63) | ((y & 63) << 6)`，取模变成与、除法变成移位。想支持非 64 的 flat，就得引入一次真除法，逐像素成本立刻上涨。扇区里存的是 8 字符**名字**而不是索引，所以"叫什么"和"是什么"是两次解引用。

`F_SKY1` 是一个**占用了 flat 名字槽位的标记**，它自己那 4096 字节内容是垃圾。它必须从 flat 表里剔除，同时任何"按名字取 flat 图"的路径都要能回答"这是天空"而不是"没找到"。当普通 flat 处理的后果：天空变成一张随机噪声，或者干脆崩溃。

天空本身是另一回事：`SKY1` 是一张**正常的纹理**（也走 PNAMES/补丁拼装），宽 256，是一张可以横向环绕的全景图。它的绘制与墙完全不同：

```
第 x 列的天空:
    水平角 = 视线角 + (x - 视口中心) × 每像素对应的角度
    贴图列 = 水平角 → 取高 8 位  & 255        // 每 1.4° 一列，整圈正好 256 列
    没有缩放，没有距离，没有深度
```

映射只依赖**角度**，所以天空天然不参与透视：走近不会变大，不需要深度值，任何前景都能直接盖上去。这也解释了为什么"按角度取列"要用 BAM 右移来做——一次移位就是一次 1/256 圆的量化。

## 精灵 lump：名字里编着装法

```
名字语法  PPPP F RR   （6 字符）
    PPPP = 精灵名（4 字符）
    F    = 帧字母（'A'..'Z'，最多 29 个有效帧）
    RR   = 旋转号 0..8
8 字符名 = 同一个 lump 要装两个槽位，第二个是水平镜像：
    PPPP F1 R1 F2 R2      例 POSSA2A8
        → POSS 帧A 旋转2：原图
        → POSS 帧A 旋转8：同一张图，左右翻转后使用
```

旋转号语义：`0` = 这个帧不分朝向，八个视角共用一张（道具、血渍、装饰几乎全是 0）；`1..8` = 八分之一圆的槽位，每个覆盖 45°。为什么要镜像对：左右两侧本来就该长得一样，与其存 8 张占 8 份内存，不如存 5 张、复用时翻转。所以"解码一次、装进两个槽位"是**必须的**，不是优化：

```
install(lumpname):
    (spr, F1, R1) = 解析名字[0..5]
    pic = 解码补丁(lumpname)                    // 只解一次
    slot[spr][F1]['0'..'8'][R1] = { pic, flip = false }
    if 名字长度 == 8:
        (F2, R2) = 名字[6], 名字[7]
        slot[spr][F2][R2] = { pic, flip = true }   // 同一份像素，绘制时按列倒读
```

`flip` 要留到绘制阶段实现（取 `width-1-u`），别在这里真的复制一份翻转图：内存翻倍，而翻转的时机本来就在逐列取像素时，几乎零成本。

一个容易忽略的坑：**帧字母是字符不是序号**，合法范围是 29 个（`'A'..'Z'` 之外还包含 `[`、`\`、`]` 三个符号，原版的判据是 `frame-'A' >= 29` 报错）。任何直接把字符当数组下标的写法都要先查范围，否则一个畸形名字就写出数组边界。

## 动画 flat：没有 ANIMATED 时怎么办

flat 会动（水流、岩浆、血、电子门框）。有两种信息来源：**数据**（DOOM II 的 WAD 里有 `ANIMATED` lump，明确写着"哪个 flat 是第几帧、属于哪一组"）和**硬编码表**（初代 DOOM 就是这么干的，源码里手写 10 组名字）。如果你的目标资源里没有 `ANIMATED`——初代 WAD、很多 Freedoom 版本都没有——那么**抄一份组列表是合法的本地标定**，因为它正是原版在同样的数据面前做的事。

```
animGroups = [ [SWST1, SWST2, SWST3, SWST4, SWST5, SWST6],
               [BLOODY1..4], [LAVA1..3], [FIRE1..3], ... ]   // 顺序 = 播放顺序
phase[group][k] = 该组第 k 帧的启动延迟（帧数），用来打散不同组的同步

取 flat 图(name):
    g = 反查表[name]
    if g 不存在: return 普通图(name)
    k = (关卡时间/推进周期 + phase[g][name]) mod g.size
    return 普通图(g[k])
```

两条规矩。**一，替换发生在"名字→图"这一层，不在扇区解析层。** 扇区的 `floorpic` 是永远不变的名字，每 tic 变的是映射；去改扇区，存档和机关立刻乱套。**二，时间基准必须是关卡 tic，不能是渲染帧或系统时钟。** 否则动画速度跟着帧率跑，掉帧的机器上水流更快，而且任何"跑 N 个 tic 再断言"的检查都不可复现——原版正是把 `leveltime` 传进渲染器来喂贴图动画的。

## RGBA8888：这本书用的打包约定

```
一个 texel = uint32，内存小端顺序是 B, G, R, A
    texel = (A<<24) | (R<<16) | (G<<8) | B
本书的解码器只产生两种状态：
    0xRRGGBBFF   画了（完全不透明）
    0x________00 没画
绝不产生中间 alpha。
```

好处是解码只需一次"索引→颜色 | 0xFF"或运算；透明空洞保留原来的颜色位，反正用不上。

**它制造的坑**：alpha 为 0 同时是两件事的合法编码——"这里没有 texel"（补丁的空洞）和"这里是一个半透明的黑"（混合特效要的）。混在一个通道里，你就只能有前者。所以规矩是：**在资源解码层，alpha 是一个布尔量**。副作用是正面的：既然 `alpha == 0` 精确地意味着"这一格没被画过"，渲染器就可以把它当**未涂色哨兵**用——可视平面判断"这个像素被地板盖住了没有"、判断"这个 texel 是不是贴图空洞"，共用同一个位，于是"贴图漏画"和"贴图本来就有洞"第一次变得可以区分（第 07 章、第 16 章都会用到这个哨兵）。**而一旦你允许中间 alpha 进入（半透明特效、淡入），这个哨兵立刻失效**，必须换成显式的覆盖位图。这就是"用 alpha 当标记"这项便宜的真正价格。

## 这样做的代价 / 放弃了什么

- **常驻缓存让启动简单，换来内存 = 所有用过的 lump 之和。** 真需要省的时候，该淘汰的是派生产物，不是原始 lump。
- **纹理在加载期一次拼成 bitmap**，于是它不能随分辨率改变：想支持任意缩放贴图，就得把拼装变回运行时路径，或为每种尺寸各存一份。"永远是 64 的倍数 + 整数缩放"把这个问题消解掉了一半，但没有全部。
- **索引色 + 双查表在 1993 年省算术，今天费内存。** RGBA8888 是索引位图的 4 倍体积，而且丢掉了"换一套表就整体变暗"的 O(1) 特效：发光、受击红、辐射护目镜全都要改成逐像素或后期处理。
- **硬编码动画组不会跟随别人的替换包。** 新加一组水流动画而你的表里没有，它就是不动。这是本地标定的直接价格，唯一的缓解是加一条检查：已知前缀的 flat 要么在表里，要么明确不在。
- **8 字符名字是死的。** 长名字、类型标签、扩展元数据一概没有。任何扩展只能塞进"未使用字段"或靠命名约定伪造，两者都没有格式保证——要么自己加校验，要么承受静默错位。

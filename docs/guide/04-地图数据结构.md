# 04 地图数据结构

## 不做这件事会怎样

一张 DOOM 地图是九个 lump。九个 lump 之间**互相用下标引用，但没有任何一个自带类型说明**，于是下面四种事故会依次发生：

- **整张图错位。** 记录步长算错一个字节——比如把线定义当 12 字节读（实际 14）——从第 2 条线开始，每个字段都是别人的字段的一部分。症状是"地图看起来像被风化的方格"，而错误其实发生在第一条记录之后。
- **只画出一半地图，或者无限递归。** 你把顶点坐标缩放成定点之后，在某处又缩放了一次。所有几何大了 65536 倍，BSP 的"在哪一侧"判定于是永远给出同一侧，遍历一路走到最深。
- **每面墙的贴图左右镜像、每扇门找错方向，而且一处都不崩。** 你把"side 0 是哪一边"的符号约定写反了。这是最可怕的一类 bug：它不违反任何局部一致性，因为整个世界都被镜面化了。
- **帧率被查找拖死。** 你在绘制循环里从 seg 出发去找它属于哪条线、哪一面、哪个扇区，甚至去比较贴图名字字符串。一帧几千次 × 每秒三十次，全花在索引和 `strcmp` 上。

这四条的解法分两层：**格式要按字节钉死**（这一层没有商量余地，因为数据是别人产的），**派生要在加载期做完一次**（这一层是设计自由）。

## 九个块，逐个钉死

地图名有两种方案：`MAP01`… 和 `E1M1`…（后者还额外有一批 `BEHAVIOR`/特殊 lump）。下面按记录大小列表，所有字段都是**小端 int16**，除非注明。

### THINGS（10 字节/条）—— 玩家、怪物、道具、灯光装饰

| 偏移 | 字段 | 含义 |
|---|---|---|
| 0, 2 | x, y | 地图单位（**不是**定点） |
| 4 | angle | 朝向，**单位是"度"**，0=东、90=北；要变成 BAM 得走一次换算，不能移位 |
| 6 | type | 物件编号：1–4 是玩家起始点，2001+ 是怪物，2005 是武器，2028 是道具，4001 是装饰灯光 |
| 8 | flags | 0x01 单人在场、0x02 合作、0x04 死斗、0x08 未用、0x10 简单、0x20 普通、0x40 困难 |

flags 决定"这张图在某个游戏模式下有哪些东西"，所以它必须在**生成物件**时被读，不能等用到再读：漏掉难度位的结果是"简单难度下出现了本该只在困难里出现的怪物"，而它不会报错。

### LINEDEFS（14 字节/条）

| 偏移 | 字段 | 含义 |
|---|---|---|
| 0, 2 | v1, v2 | 顶点索引。**v1→v2 这个方向定义了左右** |
| 4 | flags | 见下 |
| 6 | special | 机关编号，0 = 无 |
| 8 | tag | 一个"名字"，与扇区的 tag 呼应 |
| 10, 12 | sidenum[2] | **sidenum[0] = 右手面定义，sidenum[1] = 左手面定义**；−1 表示该侧不存在 |

线定义的 flags（有意义的几位）：

| 位 | 值 | 名字 | 谁在用 |
|---|---|---|---|
| 0 | 1 | 阻断行走 | 碰撞 |
| 1 | 2 | 阻断怪物行走 | AI + 碰撞 |
| 2 | 4 | 双面 | 参考用（见下） |
| 3 | 8 | 上对齐反转（不按顶贴） | 渲染 pegging |
| 4 | 16 | 下对齐反转（不按底贴） | 渲染 pegging |
| 5 | 32 | 本线带机关 | 机关 |
| 6 | 64 | 上锁 | 机关 |
| 7 | 128 | 越过障碍 | 机关/传送 |
| 8 | 256 | 重复触发 | 机关 |

高位在不同文档里名字互相矛盾。本书的纪律是：**只实现你的地图上真的出现的位**，其余一律忽略并在注释里写明（第 11 章讲怎么用地图反证语义）。另外一条重要区分：渲染判断"这面墙是否双面可见"用的是 **`sidenum[1] != -1`**，不是 flag 的 bit 2。两者在正常工具产出的地图上等价，但等价不是因果——几何上有没有对面，只由有没有对面定义决定。

### SIDEDEFS（30 字节/条）

| 偏移 | 字段 | 含义 |
|---|---|---|
| 0 | textureoffset | U 偏移（地图单位） |
| 2 | rowoffset | V 偏移（地图单位） |
| 4 | toptexture[8] | 上段贴图：本侧天花板到对面天花板之间 |
| 12 | bottomtexture[8] | 下段贴图：本侧地板到对面地板之间 |
| 20 | midtexture[8] | 中段贴图：单面墙的全部，或者门的门体 |
| 28 | sector | 这一面所属于的扇区索引 |

最后一列是整个地图里最重要的一列：**扇区归属不在几何里，在面定义里。** 一条线的两侧属于两个不同扇区，就体现为两个面定义各自指向不同扇区。而"side 0 是 v1→v2 的右手边"这个约定，配上"+X 东、+Y 北、逆时针为正"的坐标，给出一个必须写对一次的叉积：

```
cross = (v2.x - v1.x) * (p.y - v1.y) - (v2.y - v1.y) * (p.x - v1.x)
cross > 0  →  p 在左手边  →  用 sidenum[1]
cross < 0  →  p 在右手边  →  用 sidenum[0]
```

符号写反的后果前面说过了：整个世界被镜像，而每一处都自洽。所以**这条约定必须有一条常驻检查**，而不是靠"看起来对"。最便宜的一条是：对任意一个双面 seg，取它的面定义指向的那个扇区，断言该扇区的包围盒（或一个代表点）落在 seg 的对应侧。这张检查在示例仓库里救了不止一次——因为把符号写反不需要改动任何渲染代码，只需要改动一次比较的方向。

### VERTEXES（4 字节/条）：int16 x, y。就这些。
### SEGS（12 字节/条）—— BSP 切出来的线片段

| 偏移 | 字段 | 含义 |
|---|---|---|
| 0, 2 | v1, v2 | 段自己的端点（顶点索引）。**新端点可能是切分时造出来的** |
| 4 | （未使用） | 早期版本的角度字段，工具随便填，读它一定错 |
| 6 | linedef | 它来自哪条线定义 |
| 8 | side | 用哪一面：0=右，1=左 |
| 10 | offset | 段的起点处，整条贴图累计到第几列（工具算好的） |

最后一条要说清：`offset` 是**沿这条线从 v1 出发到本段起点，贴图已经推进了多少列**（含线的 textureoffset 与各补丁宽度的累加）。有了它，你不必从线的起点重新计算 U；没有它（或者你忽略它）而被 BSP 切过的长墙上，每一段都从贴图第 0 列重新开始，接缝处出现一条一条竖直的重复花纹。

**为什么会有 seg 这个东西**：BSP 需要每片叶子是凸的，于是它必须把边界切成"完全落在分割线某一侧"的小片段。所以：

> **一条 linedef 可以被切成任意多段 seg。"一段的长度"不是"一条线的长度"；一段属于某片叶子的边界，一条线属于地图几何。**

这条区别直接决定代码里该用哪个：投影、裁剪、贴图 U 起点用 **seg**（因为它才是"这一片里能看到的那部分墙"）；机关触发、碰撞、门的开合面积用 **linedef**（因为机关作用于整条线，而不是它落在某片叶子里的那截）。混用的症状很具体：一扇被切成两半的门，只有半扇会动。

### SSECTORS（4 字节/条）：int16 segcount, int16 firstseg

段的连续性是工具给的承诺：某子扇区的 seg 就是 `SEGS[firstseg .. firstseg+segcount)`。没有 seg 列表、没有指针，只有一个区间——这也是渲染器可以把它当数组扫的原因。子扇区属于哪个扇区**不存**，靠它的第一个 seg 的正面推出（第 05 章讲这件事的代价）。

### NODES（28 字节/条）—— BSP 内部节点

| 偏移 | 字段 | 含义 |
|---|---|---|
| 0, 2 | x, y | 分割线起点 |
| 4, 6 | dx, dy | 分割线向量；**可以是 0**（退化节点） |
| 8..23 | 两个子区域的包围盒 | 每盒 4 个 int16，顺序是 **top, bottom, left, right** |
| 24, 26 | children[2] | 子下标 |

`dx = dy = 0` 的退化分割线在真实地图里存在。它意味着"这条线无法把任何东西分开"，正确处理是**一律当前进**；如果你直接算叉积再比较，会得到"两侧都不为真"，于是一个子树永远进不去，或者两边都进去（画面重复、帧率腰斩）。包围盒的字段顺序不是 `minX,minY,maxX,maxY`，写成后者不会崩，只会让快速排斥**偶尔太松或偶尔太紧**——后者会裁掉看得见的东西，而且几乎无法从画面上定位。

子下标最高位是标志：`if (child & 0x8000) 是子扇区下标，否则是节点下标`。这个 15 位掩码就是"最多 32768 个子扇区"的由来。

### SECTORS（26 字节/条）

| 偏移 | 字段 | 含义 |
|---|---|---|
| 0, 2 | floorheight, ceilingheight | 地图单位，整数值 |
| 4 | floorpic[8] | flat 名（可能是 `F_SKY1`） |
| 12 | ceilingpic[8] | flat 名（可能是 `F_SKY1`） |
| 20 | lightlevel | 0..255 |
| 22 | special | 扇区机关类型（持续效果：有害地板、秘密、灯光闪烁、门自动开） |
| 24 | tag | 一个"名字"，被线定义的 tag 引用 |

文件里就这些。运行时你要往上加：地板/天花板的移动者指针、当前动画的灯光档、伤害累计器。**加字段可以，改顺序不行**——这九个格式是只读契约。

### 机关的两半，以及 tag 为什么不是指针

`线.special + 线.tag` 与 `扇区.special + 扇区.tag` 是同一套机关系统的两半：**线是触发器（按下开关、走过缝隙），扇区是被影响的对象（会动的那块地板/天花板、会闪的灯、有害的水）。** `线.special` 说"这是什么动作"，`扇区.special` 说"这里持续地有什么事在发生"。

关键在于 tag 只是一个 **16 位整数名字**，不是索引。为什么不能是索引：一张地图上的一个开关要影响的是一**群**扇区（一个房间的四块平台），这群扇区是关卡作者画完几何之后才决定的，而且它们**在地图上不相邻**——一个开关可能同时抬起两栋楼里的各一块地板。任何"指针"都只能指向一个，也必然在作者搬动房间时失效。所以工具的做法是：给一个房间起一个号（tag = 3），给任何想影响它的机关写上同一个号；运行时用一次全表扫描建立"tag → 扇区列表"。

```
初始化（进关卡一次）：
    for s in sectors: taggedGroups[s.tag].push(s)       // 只收集非 0 的 tag
    for l in linedefs where l.special != 0:
        按 special 编号建立机关对象，绑定 taggedGroups[l.tag] 与 l 自己
```

这张表必须**建在关卡初始化，用在这一 tic 的机关逻辑里**，绝不能建在绘制里。同一批 tag 也可能指向"一条线自己"（比如门的另一侧）——那些不需要表。而"0 号 tag"是保留值：意思是"没有目标"，所以建表时要跳过，否则你会给每一个不带机关的扇区都挂上一个免费分组。

### BLOCKMAP（长度不定）—— 游戏逻辑唯一的空间索引

区块图把地图按 128×128 地图单位分格，每格记录"可能与这一格相交的**线**"。

```
int16 orgx, orgy            第 (0,0) 格的左下角坐标
int16 columns, rows
int16 offset[columns*rows]  每格列表的下标（相对 lump 起始，单位是"16 位字个数"，不是字节）
然后逐格：
    int16 -1                哨兵（原版先跳过一个 -1 才开始读）
    int16 linedef 索引 …
    int16 -1                终止（= 0xFFFF）
```

```
查询一个包围盒 (x1,y1)-(x2,y2):
    bx1 = floor((x1 - orgx) / 128);  bx2 = floor((x2 - orgx) / 128)     // 同理 by
    for by in by1..by2:
        for bx in bx1..bx2:
            list = (int16*)lump + offset[by*columns + bx]
            assert list[0] == -1
            for p = list+1; *p != -1; ++p:
                候选线 += linedefs[*p]
```

整个碰撞系统便宜的唯一原因就在这两行循环的边界上：玩家包围盒 32×32，格子 128×128，所以 `bx2-bx1` 和 `by2-by1` **最多是 1**——一次查询通常是 1 格，偶尔 2×2 = 4 格。怪物是 64×64，最多 3×3 = 9 格。也就是说，不管地图有 500 条还是 5000 条线，每次移动判定你只检查十几条到几十条线。这就是为什么不需要四叉树、不需要 BVH、不需要任何额外的空间结构——**给它一个包围盒，它给你一个小候选集，剩下的活由线段与点的精确判定收口。**

三个格式陷阱：offset 是"字数下标"，写成字节偏移你会拿到错位的线表（症状是"墙上有些线根本挡不住人"）；终止符既可能是 −1 也可能是 0xFFFF，读成无符号还是带符号决定了你能不能发现坏数据；以及**格表必须落在前 32768 个字内**——offset 只有 16 位，非常大的地图会把下标写溢出，这是极少数会真正咬人的格式极限之一。

还有一个语义陷阱，比格式更重要：**区块图只给你线，不给你扇区。** 你拿到候选线之后，还得逐条判断"这条线是不是真的跨过我的包围盒"（用第 03 节那个叉积），才知道哪条线 defines 我脚下的高度。这一步是碰撞代码的正文（第 09 章），不是可以跳过的样板。另外，物件（mobj）不在区块图里：那是一张**运行时**由同样尺寸建出来的"格 → 物件链表"表，会随物件移动增删。

## 派生：加载期算一次，绘制期永远不再算

九个块读完之后，有一件事必须马上做。渲染需要"这个 seg 的正面扇区和反面扇区"，但文件里 seg 只有一个 `linedef` 下标和一个 `side` 标志。所以要解三跳：

```
加载期（每张地图一次）：
    for v in vertexes: v.xf = fixed32(v.x) << 16        // 只做这一次
    for n in nodes:    同样 <<16
    for sg in segs:
        line = linedefs[sg.linedef]
        side = sidedefs[ line.sidenum[sg.side] ]
        sg.front = sectors[ side.sector ]
        other = 1 - sg.side
        sg.back = (line.sidenum[other] == -1) ? null
                                             : sectors[ sidedefs[line.sidenum[other]].sector ]
    顶点坐标另存一份 int16 原值（或只存定点，二选一，别混）
```

**为什么必须缓存**：那三跳是 3 次数组索引 + 1 次条件 + 1 次减法，而一帧里要对几千个 seg 做这件事；再加上"名字 → 贴图"的查找，不做派生缓存就等于每帧重做一遍世界。这条规矩的名字可以叫"**派生在加载，绘制只读结果**"：渲染循环里不允许出现字符串比较、不允许出现扇区解析、不允许出现 sqrt 与除法之外的换算。

| 派生量 | 在哪算 | 留给绘制的代价 |
|---|---|---|
| seg 的正/反面扇区 | 加载 | 每帧数千次三级索引 |
| 贴图名 → 纹理下标 | 加载（或首次使用） | 每帧几万字符串比较 |
| 纹理 → 拼好的 RGBA | 加载 | 每帧逐像素重拼（第 03 章） |
| 顶点 int16 → 定点 | 加载 | 二次缩放的温床 |
| tag → 扇区分组 | 关卡初始化 | 每次触发全表扫描 |
| 区块图的 orgx/列数 | 加载（顺手校验尺寸） | 每格一次除法与边界检查 |
| 线的方向向量与长度 | 按需，但**别在绘制循环里** | 定点开方很贵 |

关于**二次缩放**要单独强调，因为它是静默的。顶点、节点、扇区高度、thing 坐标在文件里都是 **int16 地图单位**；引擎内部它们应当是定点。缩放只发生在解析函数内部，一次。之后任何地方再写 `<< 16`，数值就大 65536 倍。有些字段则**永远不该**变成定点：各类下标（顶点号、线号、扇区号）、`lightlevel`（0..255 的整数档）、`THINGS.angle`（度，要走度数→BAM 换算而不是移位）。最好的防御是让类型名替你说话：`mapUnits` 与 `fixed32` 是两个类型，把它们搞混应当编译不过，而不是靠人眼。

## 这样做的代价 / 放弃了什么

- **内存翻倍。** 原始记录和派生视图同时在（一份 int16 顶点、一份定点顶点；seg 多出的正反面索引）。换关卡时必须整体丢弃重建，漏一处就是"拿旧地图的扇区下标去查新地图"——这类 bug 表现为随机崩溃，很难归因。
- **启动时间变长。** 解析 + 建表 + 拼装都在进关卡之前，第一次看到画面的延迟是这些之和。想要"秒开"就得改成惰性派生，而惰性派生会把"绘制期不许算"的规矩换成"首次访问时算"，于是你的帧时间不再可预测。
- **只读契约把你的表达力锁死在 1993 年的字段里。** 想要"这面墙是可破坏的""这个扇区属于第 3 层光照"这类新信息，只能占用未使用字段（比如 seg 偏移 4 那个"未使用"）或者靠命名约定伪造，而"未使用"没有文档保证——别人的工具可能往里写东西。
- **放弃了几何之外的健壮性。** 区块图的分格大小（128）是写死在数据里的假设；一个包围盒比格子大的物件（原版某些装饰是 128 以上）会让"最多 2×2 格"的推算失效，而格式并没有任何字段提醒你这一点。
- **放弃了对坏地图的宽容。** 上面钉死的每一种步长、每一个哨兵，都是"要么严格符合、要么致命报错"。你可以选择宽松（跳过坏记录继续跑），但那样你会拿着一张自己都不确定长什么样的地图去做后续所有判断。这本书的立场是：**格式问题一律当场报错，语义问题才用检查去慢慢缩小。**
